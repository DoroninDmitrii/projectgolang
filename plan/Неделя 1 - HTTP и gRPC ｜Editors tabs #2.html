Неделя 1 — HTTP и gRPC ​

Цели недели ​

Чему вы научитесь

  • Поднимать HTTP-сервер и обрабатывать JSON
  • Поднимать gRPC-сервер и реализовывать методы
  • Вызывать gRPC-сервис из HTTP-хендлера
  • Обрабатывать ошибки между сервисами

Задание ​

На этой неделе вам предстоит реализовать три микросервиса для управления заказами на постройку космических кораблей и связать их между собой.

Архитектура системы ​

x9ok5

Компоненты космического корабля ​

Космический корабль состоит из именованных слотов (по одному компоненту каждого типа):

СлотКомпонентОбязательность
hullКорпус (1 шт.)✅ Да
engineДвигатель (1 шт.)✅ Да
shieldЩит (1 шт.)❌ Нет
weaponВооружение (1 шт.)❌ Нет

Важно

Каждый слот может содержать только один компонент. Нельзя установить два двигателя или три щита — строго по одному на слот.

Правила сдачи ​

Два PR

Домашнее задание сдаётся строго в ДВУХ PR:

  1. Первый PR — контракты (proto + OpenAPI) + генерация кода
  2. Второй PR — реализация сервисов

Сдача в одном PR = задание не принято. Сначала согласуем контракты, потом проверяем код.

Русский язык

Весь пользовательский текст в коде должен быть на русском языке:

  • Тексты ошибок
  • Сообщения логов (slog.Info("..."))
  • Комментарии в коде

Исключения — имена функций, переменных, пакетов, JSON-теги, HTTP-пути и другие технические идентификаторы остаются на английском.

Проверки перед каждым PR

bash
task format     # Форматирование кода
task lint       # Линтер без ошибок
task test:api   # API-тесты (только для второго PR)

Dot-файлы (.golangci.yml)

Ограничения этой недели ​

Почему так?

На первой неделе концентрируемся на связке HTTP↔gRPC. Архитектура, слои, паттерны — на следующих неделях.

Архитектура:

  • ❌ Не разделяйте код на слои (api/, service/, repository/) — вся логика в одном пакете
  • ❌ Не используйте dependency injection — создаём клиенты напрямую в main
  • ❌ Не выносите модели в отдельные файлы — структуры в том же пакете

Инфраструктура:

  • ❌ Не подключайте базу данных — используем map в памяти
  • ❌ Не добавляйте метрики/трейсы — это неделя 7
  • ❌ Не настраивайте конфиги (env, yaml) — хардкодим порты

Бизнес-логика:

  • ❌ Не делайте резервирование деталей — просто проверяем stock_quantity > 0
  • ❌ Не реализуйте идемпотентность
  • ❌ Не добавляйте авторизацию — это неделя 6
  • ❌ Не валидируйте совместимость деталей — любой hull + любой engine = ОК

Логирование:

  • ✅ Используйте slog из стандартной библиотеки

Обработка ошибок:

  • gRPC сервисы — создают ошибки через status.Error() / status.Errorf() с нужным gRPC кодом
  • HTTP сервис — маппит gRPC коды в HTTP статусы через status.FromError()
  • Wrapping ошибок (fmt.Errorf("...: %w", err)) появится на неделе 2 с разделением на слои

Почему pkg/, а не всё в cmd/main.go?

Бизнес-логика вынесена в pkg/, а cmd/main.go только создаёт и запускает сервер. Это позволяет API-тестам импортировать реализацию напрямую и запускать через bufconn (in-memory gRPC) — без реальных портов и процессов.

Тесты ​

Тесты автоматически запускают и останавливают все три сервиса — вручную ничего поднимать не нужно:

bash
task test:api

Как это работает?

Go-тесты в tests/api_test.go используют TestMain для запуска сервисов в памяти — gRPC-серверы через bufconn (без реальных портов), HTTP-сервер через httptest. Все три сервиса работают в том же процессе, что и тесты.

Основные сценарии (happy path)
  1. Получение списка деталей из Inventory (gRPC)
  2. Получение конкретной детали по UUID
  3. Создание заказа с hull + engine
  4. Проверка статуса PENDING_PAYMENT
  5. Оплата заказа
  6. Проверка статуса PAID

Corner cases и обработка ошибок
  • Некорректный формат UUID → 400 Bad Request
  • Несуществующий order_uuid → 404 Not Found
  • Несуществующий компонент (hull/engine/shield/weapon) → 404 Not Found
  • Попытка оплатить уже оплаченный заказ → 409 Conflict
  • Попытка оплатить отменённый заказ → 409 Conflict
  • Попытка отменить оплаченный заказ → 409 Conflict
  • Попытка отменить уже отменённый заказ → 409 Conflict
  • Отсутствие обязательных полей (hull_uuid, engine_uuid) → 400 Bad Request
  • Невалидный payment_method → 400 Bad Request

Keepalive конфигурация ​

Как в уроках

gRPC серверы и клиенты должны настраиваться с keepalive параметрами — точно так же, как в примерах первой недели. Вынесите параметры в именованные константы:

go
const (
    grpcMaxConnectionIdle     = 15 * time.Minute
    grpcMaxConnectionAge      = 30 * time.Minute
    grpcMaxConnectionAgeGrace = 5 * time.Second
    grpcKeepaliveTime         = 5 * time.Minute
    grpcKeepaliveTimeout      = 1 * time.Second
    grpcMinPingInterval       = 5 * time.Minute
)

// Создание gRPC соединения при старте (в main)
conn, err := grpc.NewClient("localhost:50051",

        Timeout:             3 * time.Second,

Маппинг PaymentMethod между HTTP и gRPC ​

Важно

В HTTP API (OpenAPI) значения PaymentMethod — короткие: CARD, SBP, CREDIT_CARD, INVESTOR_MONEY.

В gRPC (proto) — с префиксом: PAYMENT_METHOD_CARD, PAYMENT_METHOD_SBP и т.д.

При вызове PaymentService.PayOrder из OrderService необходимо преобразовать HTTP-значение в proto enum.

HTTP коды ответов:

КодСитуация
201Заказ успешно создан
400Невалидный запрос (отсутствует hull_uuid/engine_uuid или некорректный формат UUID)
404Компонент не найден в InventoryService
409Компонент отсутствует на складе (stock_quantity = 0)

Поведение:

  1. Валидация:
    • hull_uuid и engine_uuid обязательны (иначе 400)
    • Все переданные UUID должны соответствовать формату UUID (иначе 400)
  2. Получает все детали одним запросом через InventoryService.ListParts(uuids: [...])
  3. Проверяет, что все детали существуют (иначе 404)
  4. Проверяет, что stock_quantity > 0 для каждой детали (иначе 409)
  5. Вычисляет total_price как сумму цен всех компонентов
  6. Генерирует order_uuid (UUID v4)
  7. Сохраняет заказ со статусом PENDING_PAYMENT

404Заказ не найден
409Заказ уже оплачен или отменён

Поведение:

  1. Находит заказ по order_uuid
  2. Проверяет, что статус = PENDING_PAYMENT (иначе 409)
  3. Вызывает PaymentService.PayOrder, передаёт order_uuid и payment_method
  4. Получает transaction_uuid из ответа PaymentService
  5. Обновляет заказ: статус → PAID, сохраняет transaction_uuid и payment_method

POST /api/v1/orders/{order_uuid}/cancel — отмена заказа ​

Отменяет заказ, который ещё не был оплачен.

Тело запроса: пустое или {}

Ответ (200 OK):

json
{}
1

Успех определяется HTTP-кодом 200. Тело ответа пустое.

HTTP коды ответов:

КодСитуация
200Заказ успешно отменён
400Некорректный формат UUID в path
404Заказ не найден
409Заказ уже оплачен и не может быть отменён

Поведение:

  1. Находит заказ по order_uuid
  2. Проверяет статус:
    • PENDING_PAYMENT → можно отменить
    • PAID → возвращает 409 Conflict
    • CANCELLED → возвращает 409 Conflict (уже отменён)
  3. Обновляет статус на CANCELLED

Критерии приёмки ​

  • Все 4 эндпоинта реализованы строго по OpenAPI-контракту
  • Обработка статусов заказа реализована корректно
  • Заказы корректно сохраняются и обновляются в map
  • Хранилище защищено от гонок данных (sync.RWMutex)
  • Валидация запросов и обработка ошибок присутствует
  • Интеграция с InventoryService и PaymentService работает корректно

Подсказки ​

  • UUID можно сгенерировать с помощью github.com/google/uuid
  • Для хранения используйте map[string]*Order с sync.RWMutex
  • gRPC клиенты создаются один раз при старте сервиса
  • При вызове gRPC используйте context.WithTimeout для установки таймаута
  • Обрабатывайте gRPC ошибки через status.FromError(err)

Поведение методов ​

  • GetPart:

    • Валидирует формат UUID — если некорректный, возвращает INVALID_ARGUMENT
    • Ищет деталь по UUID в map
    • Если не найдена — возвращает NOT_FOUND

  • ListParts:

    • Если uuids не пустой — возвращаются именно эти детали (part_type игнорируется):
      • Валидирует формат каждого UUID
      • Если хотя бы один UUID не найден — возвращает NOT_FOUND
      • Порядок деталей соответствует порядку UUID в запросе
    • Если uuids пустой — фильтрация по типу:
      • part_type == PART_TYPE_UNSPECIFIED — возвращаются все детали
      • Конкретный тип — только детали этого типа
      • Результат сортируется по имени (алфавитный порядок)

gRPC-метод: PayOrder ​

Обрабатывает команду на оплату и возвращает transaction_uuid.

Запрос:

ПолеТипОписание
order_uuidstringUUID заказа (обязательный)
payment_methodPaymentMethodВыбранный способ оплаты (обязательный)

Ответ:

ПолеТипОписание
transaction_uuidstringUUID транзакции оплаты

gRPC коды ответов:

КодСитуация
OKОплата прошла успешно
INVALID_ARGUMENTНекорректный order_uuid или невалидный payment_method

Поведение метода (неделя 1) ​

  1. Валидация запроса:

    • Если order_uuid некорректный (пустой или невалидный формат) → возвращает INVALID_ARGUMENT
    • Если payment_method == UNSPECIFIED → возвращает INVALID_ARGUMENT

  2. Обработка оплаты:

    • Генерируется transaction_uuid (UUID v4)
    • Логируется через slog:
      go
      slog.Info("оплата выполнена", "order_uuid", orderUUID, "transaction_uuid", txUUID)
      1
    • Возвращается transaction_uuid вызывающей стороне

  3. Состояние:

    • Сервис stateless — не сохраняет информацию о транзакциях
    • Повторные вызовы с тем же order_uuid генерируют новый transaction_uuid

Критерии приёмки ​

  • Метод PayOrder реализован строго по .proto-контракту
  • Все поля запроса валидируются (формат UUID, payment_method)
  • UUID транзакции генерируется корректно (формат UUID v4)
  • Успешная оплата логируется через slog
  • Ответ возвращается в соответствии с контрактом
  • Обработка ошибок через gRPC коды (INVALID_ARGUMENT)

Подсказки ​

  • Используйте github.com/google/uuid для генерации и валидации UUID
  • Для логирования используйте slog (стандартная библиотека Go 1.21+)
  • Для возврата gRPC ошибок используйте google.golang.org/grpc/status:
    go
    import "google.golang.org/grpc/status"
import "google.golang.org/grpc/codes"

return nil, status.Error(codes.InvalidArgument, "текст ошибки")
