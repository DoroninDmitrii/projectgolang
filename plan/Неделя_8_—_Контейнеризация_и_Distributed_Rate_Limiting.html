Неделя 8 — Контейнеризация и Distributed Rate Limiting ​

Курс: «Микросервисы на Go 3.0» | Сложность: ⭐⭐⭐⭐

Трекер прогресса ​

0 из 15 выполнено 0%

Цели недели ​

Чему вы научитесь

  • Контейнеризировать Go-сервисы с multi-stage Dockerfile
  • Собирать все сервисы в единый docker-compose
  • Балансировать HTTP-трафик через Nginx (round-robin)
  • Горизонтально масштабировать сервис (--scale)
  • Реализовывать distributed rate limiter (Redis + GCRA)

Задание ​

Финальная неделя курса. Вы заворачиваете все сервисы в Docker-контейнеры, ставите перед OrderService Nginx как load balancer, поднимаете несколько инстансов OrderService и реализуете distributed rate limiter через Redis — чтобы лимит был общим для всех инстансов.

Требование: Русский язык ​

Обязательное требование

Весь пользовательский текст в коде должен быть на русском языке:

  • Тексты ошибок (errors.New("..."))
  • Сообщения логов (slog.Info("..."))
  • Комментарии в коде
  • Wrapping-сообщения в fmt.Errorf("...")

Исключения — имена функций, переменных, пакетов, JSON-теги, SQL-запросы, YAML-ключи и другие технические идентификаторы остаются на английском.

Файл Taskfile.yml из заготовки содержит дополнения к вашему существующему файлу. Не копируйте его поверх — вручную добавьте новые таски (vegeta:install, up-all, down-all, load:http) в ваш существующий Taskfile.yml.

Теория: Multi-stage Dockerfile ​

Multi-stage сборка разделяет процесс на два этапа. На первом этапе (builder) используется полный образ golang:1.26-alpine (~1 GB) — в нём компилируется бинарник. На втором этапе (runtime) берётся чистый alpine:3.23 (~10 MB), в который копируется только готовый бинарник через COPY --from=builder.

ЭтапОбразРазмерСодержимое
Buildergolang:1.26-alpine~1 GBGo компилятор, исходники, зависимости
Runtimealpine:3.23~10 MBТолько скомпилированный бинарник

Итог: финальный образ ~10 MB вместо ~1 GB. Это важно для скорости деплоя и безопасности (меньше атакующая поверхность).

container_name у масштабируемых сервисов

У order-service нельзя указывать container_name и ports — при --scale order-service=3 Docker создаёт три контейнера с уникальными именами. Если указать container_name, масштабирование сломается (конфликт имён). Порты тоже не нужны — трафик идёт через Nginx.

У остальных gRPC-сервисов (inventory-service, payment-service, iam-service, assembly-service) container_name тоже не указан — на случай, если захотите поэкспериментировать с масштабированием через --scale. Для отладки по имени контейнера смотрите реальные имена через docker ps (будут вида services-inventory-service-1). ports оставлены для удобства: проброшенные 50051/50052/50053 позволяют бить в сервис с хоста через grpcurl. При --scale их тоже нужно убрать — иначе будет конфликт портов на хосте.

Часть 2: Nginx и масштабирование ​

Теория: Load Balancing ​

Nginx выступает обратным прокси (reverse proxy) перед несколькими инстансами OrderService (см. схему в разделе «Архитектура» выше).

ПараметрЗначениеОписание
АлгоритмRound-robinЗапросы распределяются по очереди
Service DiscoveryDocker DNSNginx резолвит имя сервиса в IP всех реплик
Количество реплик--scaleЗадаётся при запуске, не в конфиге

Как работает Docker DNS ​

Nginx конфиг содержит:

nginx
upstream order_backend {
    server order-service:8080;
}
1
2
3

order-service — не один сервер. Docker DNS резолвит это имя в IP-адреса всех контейнеров этого сервиса. Количество реплик не прописывается в nginx.conf — оно задаётся при запуске через --scale order-service=3 (внутри task up-all). Nginx узнаёт о реплике автоматически через Docker DNS.

Часть 3: Distributed Rate Limiter ​

Зачем distributed? ​

С in-memory rate limiter каждый инстанс имеет свой счётчик:

OrderService #1: лимит 100 RPS → пропускает 100
OrderService #2: лимит 100 RPS → пропускает 100
OrderService #3: лимит 100 RPS → пропускает 100
Итого: 300 RPS проходит (а хотели 100!)
1
2
3
4

С distributed rate limiter все инстансы используют один счётчик в Redis:

OrderService #1 ─┐
OrderService #2 ─┼─→ Redis: общий лимит 100 RPS
OrderService #3 ─┘
Итого: ровно 100 RPS проходит
1
2
3
4

Это частый вопрос на System Design собеседованиях: «Как реализовать rate limiter при нескольких инстансах?» Нужен общий счётчик — чаще всего Redis, но подойдёт и Memcached, БД, или dedicated rate limit service.

Теория: GCRA (Generic Cell Rate Algorithm) ​

Библиотека redis_rate использует алгоритм GCRA — вариант token bucket, реализованный атомарно через Lua-скрипт в Redis:

ПараметрОписаниеПример
RateКоличество запросов в единицу времени100 per second
BurstМаксимальный всплеск200
PeriodПериод (по умолчанию = 1 сек)1s

Почему GCRA, а не обычный counter?

Обычный counter в Redis (INCR + EXPIRE) имеет проблему «boundary»: на границе окна можно отправить 2x запросов. GCRA не имеет этой проблемы — он использует «скользящее окно».

Реализация: HTTP Middleware ​

Реализуйте HTTP middleware в platform/pkg/ratelimit/middleware.go — по аналогии с тем, что разобрано на уроке. Ключевые моменты:

  • Используйте библиотеку github.com/go-redis/redis_rate/v10 и её метод limiter.Allow(ctx, key, limit)
  • В качестве ключа — путь запроса (r.URL.Path)
  • Если лимит превышен (res.Allowed == 0) — возвращайте http.StatusTooManyRequests (429)
  • Fail-open стратегия: если Redis недоступен (ошибка от limiter.Allow) — пропускайте запрос дальше. Лучше временно пропустить лишний трафик, чем полностью остановить сервис из-за проблем с Redis
  • Лимиты: 100 RPS, burst 200 (уже заданы в config.docker.yaml)

Подключение к OrderService ​

В DI-контейнере OrderService создайте redis_rate.Limiter (через redis.NewClient + redis_rate.NewLimiter) и подключите middleware к chi-роутеру.

Rate limiter должен быть первым middleware в цепочке — до auth и observability. Нет смысла проверять сессию и ходить в IAMService, если лимит уже превышен.

HTTP запрос → Nginx → OrderService:
  [Rate Limiter] → [otelhttp] → [Auth] → Router → Handler

Чего НЕ нужно делать ​

Почему так?

На финальной неделе мы фокусируемся на контейнеризации и distributed rate limiting. Не усложняем.

Resilience — не в этой домашке ​

Типичные ошибки

  • Не реализуйте Circuit Breaker — разбирается в примерах на лекции
  • Не реализуйте Retry с exponential backoff — разбирается в примерах
  • Не добавляйте per-user rate limiting — глобальный лимит на весь сервис
  • Не реализуйте adaptive rate limiting — фиксированная конфигурация
  • Не реализуйте fallback-логику — просто возвращайте ошибку 429

Docker — упрощаем ​

Типичные ошибки

  • Не используйте Docker Swarm / Kubernetes — обычный docker-compose
  • Не оптимизируйте размер образа — alpine достаточен
  • Не настраивайте CI/CD деплой — только локальная сборка
  • Не добавляйте TLS/HTTPS — plaintext для локальной разработки

Бизнес-логика — без изменений ​

Типичные ошибки

  • Не меняйте API сервисов — контракты без изменений
  • Не добавляйте новые эндпоинты — только rate limiter
  • Не меняйте Kafka-события — без изменений

CI Pipeline ​

Важно

В проекте настроен GitHub Actions CI, который автоматически запускается при создании PR.

CI проверяет:

  • task lint — код проходит линтер
  • task test:coverage — unit-тесты с проверкой покрытия ≥5%
  • task test:api — API-тесты с PostgreSQL, Redis и Kafka

Требование

CI pipeline должен быть зелёным — это обязательное условие для принятия PR.

Отладка Docker ​

bash
# Проверить, что все контейнеры запущены

# Логи конкретного сервиса

# Логи Nginx
docker logs nginx

# Перезапустить конкретный сервис
