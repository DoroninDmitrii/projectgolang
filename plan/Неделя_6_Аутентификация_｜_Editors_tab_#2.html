Неделя 6 — Аутентификация ​

Курс: «Микросервисы на Go 3.0» | Сложность: ⭐⭐⭐

Трекер прогресса ​

0 из 15 выполнено 0%

Цели недели ​

Чему вы научитесь

  • Создавать IAM-сервис (Identity and Access Management)
  • Работать с Redis (HSET/HGETALL/DEL с TTL)
  • Хешировать пароли через bcrypt
  • Реализовывать HTTP middleware и gRPC interceptor для аутентификации
  • Понимать разницу между Incoming и Outgoing gRPC metadata
  • Передавать контекст аутентификации между сервисами

Задание ​

На этой неделе вы создаёте новый сервис — IAMService, который отвечает за регистрацию, аутентификацию и хранение сессий пользователей. Затем интегрируете аутентификацию в OrderService (HTTP middleware) и InventoryService (gRPC interceptor).

Требования ​

ОДИН Pull Request

Домашнее задание сдаётся строго в ОДНОМ PR, содержащем:

  1. IAM сервис (новый сервис с PostgreSQL + Redis) и Docker Compose для его инфраструктуры
  2. Авторизационный HTTP middleware в Order сервисе
  3. Авторизационный gRPC interceptor в Inventory сервисе
  4. Поле user_uuid в таблице orders (добавлено в неделе 5) — теперь сохраняется из сессии, а не из request

Русский язык

Весь пользовательский текст в коде должен быть на русском языке:

  • Тексты ошибок (errors.New("..."))
  • Сообщения логов (slog.Info("..."))
  • Комментарии в коде
  • Wrapping-сообщения в fmt.Errorf("...")

Исключения — имена функций, переменных, пакетов, JSON-теги, SQL-запросы, YAML-ключи и другие технические идентификаторы остаются на английском.

Чего НЕ нужно делать ​

Типичные ошибки — аутентификация

  • ❌ Не реализуйте JWT — на этой неделе session-based auth (JWT — это другой подход, в курсе не рассматривается)
  • ❌ Не делайте brute force protection — упрощаем
  • ❌ Не добавляйте роли/permissions — просто аутентификация, не авторизация
  • ❌ Не кэшируйте результат Whoami — на каждый запрос вызываем IAM (кэширование добавляет сложность инвалидации)
  • ❌ Не реализуйте refresh token — при истечении сессии пользователь делает Login заново

Типичные ошибки — инфраструктура и бизнес-логика

  • ❌ Не контейнеризируйте сервисы — Docker только для инфраструктуры
  • ❌ Не добавляйте метрики/трейсы — это неделя 7
  • ❌ Не используйте Redis для кэширования — только для сессий
  • ❌ Не добавляйте новые HTTP-эндпоинты OrderService — пути, HTTP-методы и коды ответов остаются теми же. Меняется только тело запроса POST /api/v1/orders: оттуда убирается поле user_uuid (теперь оно берётся из сессии).
  • ❌ Не меняйте Kafka-события — структура OrderPaid и ShipAssembled без изменений (поле user_uuid в них уже было в неделе 5).

Безопасность

При Login не раскрываем, существует ли логин. И «логин не найден», и «неверный пароль» возвращают одну и ту же ошибку ErrInvalidCredentials — "неверный логин или пароль". Это предотвращает перебор пользователей.

Маппинг доменных ошибок IAM в gRPC-коды вынесите в единый error-interceptor iam/internal/interceptor/error.go (по аналогии с тем, как это делалось в неделях 2–5 для других сервисов) и подключите его к gRPC-серверу в app/di.go. Сами хендлеры возвращают доменные ошибки из errs, interceptor конвертирует их в status.Error(codes.*, ...) согласно таблице кодов в контрактах.

Redis — SessionRepository ​

Сессии хранятся в Redis как HashMap (HSET/HGETALL/DEL):

  1. Нет лишней сериализации/десериализации JSON
  2. Можно читать/обновлять отдельные поля без перезаписи всей сессии
  3. В redis-cli сессия читается через HGETALL без дополнительных инструментов

Redis-ключи

  • Формат ключа: session:{uuid}
  • Поля HashMap: uuid, user_uuid, login, created_at, expires_at
  • TTL: 24 часа — устанавливается командой EXPIRE после HSET
  • Redis автоматически удаляет истёкшие ключи
  • DEL идемпотентен — повторный Logout для несуществующей сессии не ошибка

Persistence-shape сессии (аналог record у Postgres-репозиториев) лежит в iam/internal/repository/redis_view/session.go — тип SessionRedisView со скалярными полями и тегами redis:"..." (uuid, user_uuid, login, created_at, expires_at), который ложится прямо в HSET без JSON-сериализации. Имя redis_view вместо record — чтобы подчеркнуть, что это представление под конкретное хранилище (Redis HashMap), а не строка таблицы. Конвертация model.Session ↔ redis_view.SessionRedisView живёт в repository/converter/session.go — точно так же, как у Postgres устроена пара record + converter.

Сервисный слой ​

Реализуйте сервисный слой IAM по аналогии с тем, как это разбиралось в уроках. Сервис зависит от двух репозиториев (UserRepository и SessionRepository) и реализует пять методов: Register, Login, Whoami, Logout, GetUser.

Входные параметры методов Register и Login вынесите в отдельный пакет iam/internal/service/input/user.go — там лежат RegisterInput и LoginInput (логин + пароль), которые приходят из API-слоя в сервис. Это та же схема, что в неделях 2–5 для Order/Inventory: API-конвертер превращает gRPC-запрос в input.*Input, сервис принимает уже валидированный input.

Детальное поведение каждого метода и gRPC-коды ошибок — в контрактах внизу страницы.

Часть 4: Аутентификация в Order и Inventory ​

Incoming vs Outgoing Context ​

Ключевое понятие

Это одна из самых частых точек путаницы в gRPC. Разберитесь с ней до начала реализации.

КонтекстГде используетсяФункция
IncominggRPC сервер (interceptor)metadata.FromIncomingContext(ctx)
OutgoinggRPC клиентmetadata.AppendToOutgoingContext(ctx, key, value)

Правило: то, что приходит — Incoming. То, что отправляешь — Outgoing. Нельзя читать Outgoing на сервере и нельзя писать в Incoming на клиенте.

Реализация ​

В OrderService и InventoryService нужны три разных компонента (все опираются на общие хелперы контекста из platform/pkg/auth/context.go):

  1. order/internal/middleware/auth.go — HTTP middleware. Читает Authorization: Bearer <session_uuid> (или заголовок X-Session-UUID), валидирует сессию через IAMService.Whoami, кладёт user_uuid и session_uuid в context через auth.WithUserUUID / auth.WithSessionUUID.
  2. order/internal/interceptor/auth.go — gRPC client / outgoing interceptor. Достаёт session_uuid из контекста (auth.SessionUUIDFromContext) и прокидывает его в исходящие gRPC-вызовы через metadata.AppendToOutgoingContext(ctx, "session-uuid", uuid). Подключается к gRPC-клиенту InventoryService в app/di.go. Без этого interceptor'а InventoryService не получит токен сессии и упадёт на проверке.
  3. inventory/internal/interceptor/auth.go — gRPC server / incoming interceptor. Читает session-uuid из incoming metadata, валидирует через IAMService.Whoami, кладёт user_uuid в контекст.

Реализуйте все три компонента по аналогии с тем, как это разбиралось в уроках. Точное поведение и коды ошибок — в контрактах внизу страницы.

Обновлённый OrderService.Create ​

В неделе 5 клиент передавал user_uuid в теле HTTP-запроса POST /api/v1/orders. На этой неделе источник значения меняется: user_uuid берётся из аутентифицированной сессии, а из request body исчезает.

Что нужно сделать:

  1. Убрать user_uuid из OpenAPI-схемы CreateOrderRequest — поле и из properties, и из required. После task ogen:gen сгенерированный orderv1.CreateOrderRequest больше не будет содержать UserUUID.
  2. Убрать UserUUID из input.CreateOrderInput — это входной тип того же запроса в сервисе, он тоже больше не несёт идентификатор пользователя.
  3. Обновить конвертер CreateOrderRequest → input.CreateOrderInput — больше нечего копировать в UserUUID.
  4. Извлечь user_uuid из контекста в service.Create — middleware уже положил его туда, используйте auth.UserUUIDFromContext(ctx). Если значения нет — верните errs.ErrUnauthorized.
  5. Заполнить order.UserUUID из контекста перед сохранением — сама модель model.Order и колонка orders.user_uuid (из недели 5) не меняются.

Что НЕ меняется

  • Путь и HTTP-метод (POST /api/v1/orders), коды ответов, структура OrderDTO в response — без изменений.
  • Колонка orders.user_uuid (миграции 00003–00005 из недели 5) — без изменений.
  • Структура Kafka-событий OrderPaid/ShipAssembled — без изменений. Поле user_uuid в них продолжает заполняться из order.UserUUID.

Unit vs API тесты

Unit-тесты проверяют бизнес-логику с моками (Redis и PostgreSQL замоканы через интерфейсы). API-тесты проверяют полный стек включая аутентификацию — сначала Register + Login, потом аутентифицированные запросы.

CI Pipeline

В проекте настроен GitHub Actions CI, который автоматически запускается при создании PR и проверяет task lint, task test:coverage (покрытие ≥5%) и task test:api. CI pipeline должен быть зелёным — это обязательное условие для принятия PR.

// err == nil → пароль верный
// err != nil → пароль неверный

Обработка unique constraint (PostgreSQL) ​

При Register два параллельных запроса с одинаковым логином приведут к unique constraint violation:

go
import "github.com/jackc/pgx/v5/pgconn"

func (r *repository) Create(ctx context.Context, user model.User) error {
    _, err := r.db(ctx).Exec(ctx, query, ...)
    if err != nil {
        var pgErr *pgconn.PgError
        if errors.As(err, &pgErr) && pgErr.Code == "23505" {
            return errs.ErrUserAlreadyExists
        }
        return fmt.Errorf("создать пользователя: %w", err)
    }
    return nil
}

Контракт: HTTP Middleware (OrderService)

Поведение ​

  1. Извлечь заголовок Authorization из HTTP-запроса
  2. Проверить формат Bearer <session_uuid>
  3. Вызвать AuthService.Whoami(session_uuid)
  4. При ошибке → HTTP 401 Unauthorized
  5. При успехе → auth.WithUserUUID(ctx, uuid) + auth.WithSessionUUID(ctx, sessionUUID) → передать дальше

Контракт: Обновлённый OrderService (user_uuid из сессии)

Источник user_uuid ​

Поле user_uuid в таблице orders появилось в неделе 5 — клиент тогда передавал его в HTTP-запросе. На этой неделе клиент его больше не передаёт: значение берётся из контекста аутентифицированной сессии (auth.UserUUIDFromContext(ctx)).

Изменения в OpenAPI ​

Из схемы CreateOrderRequest нужно убрать поле user_uuid — и из properties, и из списка required. После регенерации (task ogen:gen) тип orderv1.CreateOrderRequest больше не будет содержать UserUUID, и клиент физически не сможет его передать.

OrderDTO в response не меняется — user_uuid там по-прежнему required и заполняется из доменной модели.

SQL ​

INSERT и SELECT не меняются — продолжают работать с уже существующей колонкой user_uuid.

sql
INSERT INTO orders (uuid, user_uuid, status, created_at)
VALUES ($1, $2, $3, $4)

SELECT uuid, user_uuid, status, transaction_uuid, payment_method, created_at, updated_at
FROM orders
WHERE uuid = $1
