Требование: Русский язык ​

Обязательное требование

Весь пользовательский текст в коде должен быть на русском языке:

  • Тексты ошибок (errors.New("..."))
  • Сообщения логов (slog.Info("..."))
  • Комментарии в коде
  • Имена тест-кейсов в t.Run("...")
  • Wrapping-сообщения в fmt.Errorf("...")

Исключения — имена функций, переменных, пакетов, JSON-теги, HTTP-пути, SQL-запросы, YAML-ключи и другие технические идентификаторы остаются на английском.

Идея: app.go управляет жизненным циклом (запуск → ожидание сигнала → graceful shutdown), а di.go — это DI-контейнер с ленивой инициализацией через геттеры:

go
// di.go — каждый компонент создаётся при первом обращении (nil-check)
type diContainer struct {
    pgPool  *pgxpool.Pool
    orderRepo orderService.OrderRepository
    // ...
}

func (d *diContainer) PGPool(ctx context.Context) *pgxpool.Pool {
    if d.pgPool == nil {
        pool, err := pgxpool.New(ctx, pgDSN)
        // ...
        closer.Add("PostgreSQL pool", func(_ context.Context) error {
            pool.Close()
            return nil
        })
        d.pgPool = pool
    }
    return d.pgPool
}

pkg/app — не удаляйте при переходе на DI-контейнер

С появлением internal/app/ (DI-контейнер) может возникнуть желание удалить pkg/app/ — не делайте этого. Это тот же тестовый хелпер из недель 2–3, и он по-прежнему необходим.

API-тесты (order/tests/api_test.go) собирают все три сервиса in-process через bufconn. Тестовый код в модуле order не может импортировать internal/ пакеты из модулей inventory и payment — Go запрещает cross-module доступ к internal.

pkg/app/app.go остаётся тонкой обёрткой с функциями Interceptors() и RegisterServices(...), которые делегируют в internal/ и экспортируют минимальный API для тестов. После появления DI-контейнера обновите эти обёртки, чтобы они собирали зависимости так же, как internal/app/di.go.

Часть 2: Конфигурация ​

На неделе 3 параметры подключения были захардкожены в коде или читались из env напрямую. Теперь конфигурация становится структурированной: YAML-файл задаёт базовые значения для конкретного окружения, а переменные окружения перетирают их при необходимости.

Библиотека cleanenv ​

Используется cleanenv — одна библиотека, которая умеет и то, и другое:

  • cleanenv.ReadConfig(path, &cfg) — читает YAML-файл, затем перетирает значения из env-переменных
  • cleanenv.ReadEnv(&cfg) — читает только env-переменные (если YAML-файл не задан)

Go-структуры конфига содержат оба набора тегов — yaml для маппинга из YAML и env/env-default для маппинга из переменных окружения:

go
type pgConfig struct {
    Host string `yaml:"host" env:"POSTGRES_HOST" env-default:"localhost"`
    Port string `yaml:"port" env:"POSTGRES_PORT" env-default:"5432"`
}

Путь к конфигу определяется по цепочке: флаг -config > env CONFIG_PATH > config.local.yaml (дефолт).

Загрузка конфигурации ​

go
// config.go

const defaultConfigPath = "config.local.yaml"

// ResolveConfigPath определяет путь к конфиг-файлу по цепочке приоритетов:
// флаг -config > env CONFIG_PATH > "config.local.yaml".
func ResolveConfigPath() string {
    var cfgFlag string
    flag.StringVar(&cfgFlag, "config", "", "путь к YAML-конфигу")
    flag.Parse()

    if cfgFlag != "" {
        return cfgFlag
    }

    if envPath := os.Getenv("CONFIG_PATH"); envPath != "" {
        return envPath
    }

    return defaultConfigPath
}

// Load загружает конфигурацию: YAML-файл + env-переменные поверх.
func Load(path string) (*Config, error) {
    var cfg Config

    if path != "" {
        // ReadConfig читает YAML, затем перетирает значения из env.
        if err := cleanenv.ReadConfig(path, &cfg); err != nil {
            return nil, fmt.Errorf("загрузить конфиг из %q: %w", path, err)
        }
        return &cfg, nil
    }

    // Если путь не указан — только env-переменные.
    if err := cleanenv.ReadEnv(&cfg); err != nil {
        return nil, fmt.Errorf("загрузить конфиг из env: %w", err)
    }

    return &cfg, nil
}

.env-файлы и их потребители ​

.env-файлы (order.env, inventory.env) содержат параметры БД и используются тремя потребителями:

ПотребительКак использует
Docker Composeenv_file: ../../inventory.env — передаёт POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB в контейнер PostgreSQL
Goose (в Taskfile)Формирует DSN для миграций из POSTGRES_* переменных
Go-приложениеgodotenv.Load() загружает .env в os.Environ → cleanenv подхватывает их и перетирает значения из YAML

Что НЕ нужно в .env-файлах

Адреса серверов и клиентов (GRPC_HOST, GRPC_PORT, HTTP_HOST, HTTP_PORT, INVENTORY_ADDRESS, PAYMENT_ADDRESS) не добавляйте в .env-файлы — Docker Compose и Goose в них не нуждаются. Эти значения живут в YAML-конфигах и env-default тегах Go-структур.

.env-файлы хранят только то, что разделяется между потребителями: параметры БД.

Использование в main.go ​

go
func main() {
    configPath := config.ResolveConfigPath()

    // .env опционален — ошибка загрузки допустима.
    _ = godotenv.Load("inventory.env")

    // YAML-конфиг + env-переменные поверх.
    cfg, err := config.Load(configPath)
    if err != nil {
        slog.Error("не удалось загрузить конфигурацию", "error", err)
        os.Exit(1)
    }

    app := app.New(cfg)
    app.Run()
}

Часть 3: Platform-библиотека ​

Platform-библиотека идёт в составе boilerplate (platform/). Код closer, health check и logger готов к использованию — изучите его самостоятельно после копирования.

Не забудьте интегрировать все три компонента в свои сервисы:

  • Logger — вызвать logger.Init(level) при старте приложения
  • Closer — регистрировать ресурсы через closer.Add(...) в DI-контейнере и вызывать closer.CloseAll() при shutdown
  • Health Check — зарегистрировать на gRPC-сервере через health.Register(grpcServer)

Часть 4: DDD — доменная модель и бизнес-правила ​

На этой неделе InventoryService переходит от анемичной модели к Domain-Driven Design: rich entity с бизнес-логикой внутри, типобезопасные Value Objects и выделенный domain service для правил совместимости.

DDD только для InventoryService

DDD-модель (приватные поля, геттеры, бизнес-методы) применяется только к Part в InventoryService. Модель Part в OrderService (order/internal/model/part.go) остаётся анемичной — это простой DTO для данных, полученных по gRPC. Модель Order тоже остаётся с публичными полями — DDD для заказов будет в следующих неделях.

Зачем DDD?

В анемичной модели Part — просто контейнер данных с публичными полями, а вся логика размазана по сервисному слою. Это работает на простых CRUD-операциях, но при появлении бизнес-правил (совместимость, резервирование) приводит к дублированию логики и нарушению инвариантов (бизнес-правил, которые должны выполняться всегда).

DDD решает это: сущность сама защищает свои инварианты (нельзя зарезервировать больше, чем есть), а domain service инкапсулирует правила (скрывает логику за единым интерфейсом), затрагивающие несколько сущностей (совместимость деталей).

Компоненты с типоспецифичными свойствами ​

Детали космического корабля имеют типоспецифичные свойства, хранящиеся в properties JSONB:

ТипСвойствоОписание
HULLstrength (int)Прочность корпуса (30–200)
ENGINEclass (string: A/B/C)Класс двигателя
required_strength (int)Минимальная прочность корпуса
SHIELDshield_type (string)Тип щита: energy или plasma
WEAPONweapon_type (string)Тип оружия: laser или missile

Почему JSONB? ​

У каждого типа детали свой набор свойств. Как хранить такие полиморфные данные?

ПодходСутьПлюсыМинусы
JSONBОдна колонка properties JSONBОдна таблица, схема не меняется при добавлении типов, нативная поддержка в pgxНет type safety на уровне БД, сложнее индексировать
Nullable columnsОтдельные колонки: strength INT NULL, engine_class TEXT NULL, ...CHECK-constraints per type, обычные B-tree индексы, простые запросыКолонки растут с каждым типом, много NULL-ов, ALTER TABLE при добавлении свойств
Table-per-typeБазовая таблица parts + дочерние hull_parts, engine_parts, ...Полная type safety на уровне БДJOIN на каждый запрос, миграция при каждом новом типе, overkill для 1–2 полей
EAVpart_attributes(part_uuid, key, value)Максимальная гибкостьАнтипаттерн: нет типизации, невозможно индексировать, ужасная производительность

Выбор — JSONB, потому что:

  • По свойствам не нужны SQL-запросы — мы не делаем WHERE strength > 50. Properties читаются целиком, вся логика в Go
  • Автоматический маппинг через json.Unmarshal — zero boilerplate при конвертации record → domain
  • Частый паттерн в продакшене для полиморфных данных — полезный навык

Value Objects: Pointer Union ​

Наивный подход — один плоский struct со всеми полями всех типов:

    Strength         int
    Class            string
    RequiredStrength int
    ShieldType       string
    WeaponType       string
}

Проблема: у корпуса есть поле WeaponType — можно случайно прочитать чужое поле. Нет type safety.

Вместо этого используем паттерн Pointer Union — отдельный Value Object на каждый тип, объединённые в struct, где ровно одно поле non-nil:

Доменная модель — приватные поля, геттеры, никаких json-тегов. Сериализация — не забота домена:

go
// PartProperties — типоспецифичные свойства детали.
// Ровно одно поле non-nil — определяется типом детали.
type PartProperties struct {
    hull   *HullProperties
    engine *EngineProperties
    shield *ShieldProperties
    weapon *WeaponProperties
}

func (p *PartProperties) Hull() *HullProperties    { return p.hull }
func (p *PartProperties) Engine() *EngineProperties { return p.engine }
func (p *PartProperties) Shield() *ShieldProperties { return p.shield }
func (p *PartProperties) Weapon() *WeaponProperties { return p.weapon }

Почему Pointer Union?

Этот паттерн используется в Azure SDK, protobuf oneof в Go и других production-кодебазах. В отличие от interface{} / any, здесь не нужны type assertions — доступ к свойствам через геттеры: props.Hull().Strength(). Какое поле non-nil — определяется при конвертации из record в converter-слое.

PartType с валидацией ​

PartType — типизированная строковая константа. Конвертер (repository/converter) должен валидировать тип через конструктор NewPartType, а не кастить строку напрямую:

go
// inventory/internal/model/part_type.go

type PartType string

const (
    PartTypeUnspecified PartType = "UNSPECIFIED"
    PartTypeHull        PartType = "HULL"
    PartTypeEngine      PartType = "ENGINE"
    PartTypeShield      PartType = "SHIELD"
    PartTypeWeapon      PartType = "WEAPON"
)

// NewPartType создаёт тип детали с валидацией.
func NewPartType(s string) (PartType, error) {
    pt := PartType(s)
    switch pt {
    case PartTypeHull, PartTypeEngine, PartTypeShield, PartTypeWeapon:
        return pt, nil
    default:
        return "", fmt.Errorf("неизвестный тип детали %q: %w", s, errs.ErrInvalidProperties)
    }
}

Rich Entity: Part ​

Part — доменная сущность с приватными полями и бизнес-методами. Сущность сама защищает свои инварианты: reserved не может превысить stockQuantity и не может стать отрицательным.

go
// inventory/internal/model/part.go

// Part — доменная сущность детали космического корабля.
type Part struct {
    uuid          string
    name          string
    description   string
    partType      PartType
    price         int64
    stockQuantity int
    reserved      int
    properties    PartProperties

Конвертация record → domain ​

В репозитории данные читаются в плоский record, а затем конвертируются в доменную модель:

func PartRecordToModel(rec record.PartRecord) (model.Part, error) {
    var propsRec record.PartPropertiesRecord
    if err := json.Unmarshal(rec.Properties, &propsRec); err != nil {
        return model.Part{}, fmt.Errorf("десериализовать свойства: %w", err)
    }

    props, err := partPropertiesFromRecord(propsRec)
    if err != nil {
        return model.Part{}, fmt.Errorf("конвертировать свойства: %w", err)
    }

    partType, err := model.NewPartType(rec.PartType)
    if err != nil {
        return model.Part{}, fmt.Errorf("конвертировать тип детали: %w", err)
    }

    return model.RestorePart(
        rec.UUID,
        rec.Name,
        rec.Description,
        partType,
        rec.Price,
        rec.StockQuantity,
        rec.Reserved,
        props,
        rec.CreatedAt,
    ), nil
}

func partPropertiesFromRecord(rec record.PartPropertiesRecord) (model.PartProperties, error) {
    switch {
    case rec.Hull != nil:
        return model.NewHullProperties(rec.Hull.Strength)
    case rec.Engine != nil:
        return model.NewEngineProperties(model.EngineClass(rec.Engine.Class), rec.Engine.RequiredStrength)
    case rec.Shield != nil:
        return model.NewShieldProperties(model.ShieldType(rec.Shield.ShieldType))
    case rec.Weapon != nil:
        return model.NewWeaponProperties(model.WeaponType(rec.Weapon.WeaponType))
    default:
        return model.PartProperties{}, nil
    }
}

Бизнес-правила ​

Правило 1: Прочность корпуса ​

Корпус должен выдерживать нагрузку двигателя — hull.strength >= engine.required_strength:

  • Двигатель класса C — требует прочность корпуса strength ≥ 30
  • Двигатель класса B — требует прочность корпуса strength ≥ 70
  • Двигатель класса A — требует прочность корпуса strength ≥ 100

Например, алюминиевый корпус (strength = 50) выдержит двигатель класса C, но не класса B.

Правило 2: Конфликт щит-оружие ​

Плазменный щит (shield_type = plasma) несовместим с лазерным оружием (weapon_type = laser) — плазма создаёт электромагнитные помехи, нарушающие работу лазера. Остальные комбинации допустимы:

  • energy + laser — ок
  • plasma + missile — ок
  • energy + missile — ок

Domain Service: CompatibilityChecker ​

Правила совместимости затрагивают несколько сущностей — это ответственность domain service. Но сами условия живут на Value Objects рядом с данными, а CompatibilityChecker остаётся тонким оркестратором:

go
// CanSupport проверяет, выдержит ли корпус нагрузку двигателя.
func (h *HullProperties) CanSupport(e *EngineProperties) bool {
    return h.strength >= e.requiredStrength
}

Почему domain service, а не метод entity?

Проверка совместимости — это правило, затрагивающее несколько сущностей (корпус + двигатель, щит + оружие). Ни одна отдельная сущность Part не владеет этим знанием. В DDD такие правила выносят в domain service.

А вот Reserve() и Release() — методы entity, потому что это инвариант одной сущности (reserved ≤ stockQuantity).

Application service: ReserveParts и ReleaseParts ​

-- +goose Up

-- properties — JSONB-колонка для типоспецифичных свойств детали.
-- У каждого типа свой набор полей: у корпуса — strength, у двигателя — class и required_strength,
-- у щита — shield_type, у оружия — weapon_type. JSONB позволяет хранить их в одной таблице
-- без создания отдельных таблиц на каждый тип.
-- DEFAULT '{}' — новые детали без свойств получают пустой объект, а не NULL.
--
-- reserved — сколько единиц этой детали уже зарезервировано под заказы.
-- Доступно для новых заказов: stock_quantity - reserved.
ALTER TABLE parts
    ADD COLUMN properties JSONB NOT NULL DEFAULT '{}',
    ADD COLUMN reserved INT NOT NULL DEFAULT 0;

-- CHECK-ограничения — защита на уровне БД от невалидных состояний.
-- Даже если в коде баг, PostgreSQL не даст записать отрицательный остаток
-- или зарезервировать больше, чем есть на складе.
--
-- chk_stock_non_negative  — stock_quantity >= 0 (нельзя уйти в минус по складу)
-- chk_reserved_non_negative — reserved >= 0 (нельзя «отменить» больше, чем зарезервировано)
-- chk_reserved_le_stock   — reserved <= stock_quantity (нельзя зарезервировать больше, чем есть)
ALTER TABLE parts
    ADD CONSTRAINT chk_stock_non_negative CHECK (stock_quantity >= 0),
    ADD CONSTRAINT chk_reserved_non_negative CHECK (reserved >= 0),
    ADD CONSTRAINT chk_reserved_le_stock CHECK (reserved <= stock_quantity);

-- +goose Down

-- Удаляем в обратном порядке: сначала ограничения, потом колонки.
-- IF EXISTS — чтобы откат не падал, если миграцию применяли частично.
ALTER TABLE parts
    DROP CONSTRAINT IF EXISTS chk_reserved_le_stock,
    DROP CONSTRAINT IF EXISTS chk_reserved_non_negative,
    DROP CONSTRAINT IF EXISTS chk_stock_non_negative;

ALTER TABLE parts
    DROP COLUMN IF EXISTS reserved,
    DROP COLUMN IF EXISTS properties;

gRPC-вызов внутри транзакции — учебное упрощение

В этом примере мы делаем сетевой вызов (gRPC к PaymentService) внутри открытой транзакции.

Почему это плохо в продакшене:

  • Если PaymentService отвечает медленно — транзакция держится долго
  • Если PaymentService упал, но оплата прошла — мы откатим транзакцию, а деньги уже списаны

В рамках ДЗ этот подход допустим — он наглядно демонстрирует работу с транзакциями. Проблемы распределённых транзакций и способы их решения мы обсудим в следующих неделях.

go
// order/internal/service/order/pay.go
func (s *service) Pay(ctx context.Context, uuid string, method model.PaymentMethod) (string, error) {
    var transactionUUID string

    err := s.txManager.Do(ctx, func(txCtx context.Context) error {
        // 1. Читаем заказ в транзакции
        order, err := s.orderRepo.Get(txCtx, uuid)
        if err != nil {
            return fmt.Errorf("получить заказ: %w", err)
        }

        // 2. Проверяем статус
        if order.Status != model.OrderStatusPendingPayment {
            if order.Status == model.OrderStatusPaid {
                return errs.ErrOrderAlreadyPaid
            }
            return errs.ErrOrderCancelled
        }

        // 3. Вызываем PaymentService (gRPC внутри транзакции — учебный пример)
        transactionUUID, err = s.paymentClient.PayOrder(txCtx, uuid, method)
        if err != nil {
            return fmt.Errorf("оплатить заказ: %w", err)
        }

        // 4. Обновляем заказ
        order.Status = model.OrderStatusPaid
        order.TransactionUUID = &transactionUUID
        order.PaymentMethod = &method

        err = s.orderRepo.Update(txCtx, order)
        if err != nil {
            return fmt.Errorf("обновить заказ: %w", err)
        }

        return nil
    })
    if err != nil {
        return "", err
    }

    return transactionUUID, nil
}

Как это работает?

Unit-тесты проверяют бизнес-логику service слоя с моками. API-тесты проверяют полный стек, включая совместимость деталей, резервирование и работу с реальной PostgreSQL.

CI Pipeline ​

Важно

В проекте настроен GitHub Actions CI, который автоматически запускается при создании PR.

CI проверяет:

  • task lint — код проходит линтер
  • task test:coverage — unit-тесты с проверкой покрытия ≥40%
  • task test:api — API-тесты с PostgreSQL

Требование

CI pipeline должен быть зелёным — это обязательное условие для принятия PR.

  • Примеры из уроков четвёртой недели
  • pgx — PostgreSQL driver for Go
  • DDD in Go

Контракт: DI-контейнер

Порядок закрытия (LIFO через closer) ​

Ресурсы закрываются в обратном порядке регистрации в closer:

  1. gRPC/HTTP серверы — зарегистрированы последними, закрываются первыми
  2. gRPC-клиентские соединения — только OrderService
  3. pgxpool — зарегистрирован первым, закрывается последним

Это гарантирует: сначала перестаём принимать запросы, затем закрываем соединения к внешним сервисам, и только потом — БД.

pkg/app — тестовый хелпер ​

API-тесты (order/tests/api_test.go) собирают все три сервиса in-process через bufconn. Тестовый код в модуле order не может импортировать internal/ пакеты из модулей inventory и payment — Go запрещает cross-module доступ к internal.

Сохраните pkg/app/app.go в каждом сервисе как тонкую обёртку:

  • Interceptors() []grpc.ServerOption — возвращает gRPC-опции с интерцепторами
  • RegisterServices(grpcServer, pool) — собирает зависимости и регистрирует сервисы

Эти функции делегируют в internal/ и экспортируют минимальный API для тестов.
