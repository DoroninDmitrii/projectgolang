Часть 2: Контракты событий ​

Proto-файлы событий и обновлённый контракт InventoryService уже есть в бойлерплейте. После копирования замените your-project на имя вашего модуля и выполните task proto:gen.

Зачем Protobuf для Kafka-событий?

Protobuf гарантирует типобезопасность и обратную совместимость. При эволюции схемы старые consumer'ы продолжат работать (неизвестные поля игнорируются). Это гораздо надёжнее, чем json.Marshal/Unmarshal с произвольными структурами.

Для сериализации/десериализации используйте proto.Marshal и proto.Unmarshal из пакета google.golang.org/protobuf/proto.

Поле user_uuid — проведите его через всю цепочку ​

События OrderPaid и ShipAssembled содержат обязательное поле user_uuid — идентификатор пользователя-владельца заказа. Для его наполнения нужно добавить поле в заказ и пробросить через всю цепочку:

  1. OpenAPI — добавьте user_uuid (uuid v4, required) в CreateOrderRequest и OrderDTO.
  2. БД — добавьте колонку user_uuid UUID NOT NULL в таблицу orders тремя отдельными миграциями (см. блок ниже про трёхшаговый паттерн).
  3. Модель — добавьте UserUUID в model.Order и input.CreateOrderInput; прокиньте через репозиторий (INSERT/SELECT) и API-конвертеры.
  4. Producer OrderPaid — кладите order.UserUUID в поле user_uuid события.
  5. AssemblyService — при обработке OrderPaid сохраняйте user_uuid в доменной модели события, а при отправке ShipAssembled кладите его обратно.
  6. Consumer ShipAssembled в OrderService — декодируйте user_uuid (хотя бы для логов).

Откуда берётся user_uuid на этой неделе

Сейчас клиент передаёт user_uuid руками в теле запроса POST /api/v1/orders — любой валидный uuid v4. На неделе 6 (аутентификация) мы добавим сессии и IAM-сервис, и user_uuid будет автоматически извлекаться из сессии авторизованного пользователя — поле исчезнет из тела запроса. Ваша задача на этой неделе — просто провести его через всю цепочку «API → БД → Kafka → consumer», чтобы в неделю 6 осталось только сменить источник значения.

Трёхшаговая миграция: почему не одна ADD COLUMN ... NOT NULL

Соблазнительно добавить поле одним SQL-выражением:

sql
ALTER TABLE orders ADD COLUMN user_uuid UUID NOT NULL;
1

На пустой таблице это сработает, и в учебных тестах (testcontainers с чистой БД) проблемы не будет. Но в реальном проде с уже существующими заказами PostgreSQL отвергнет такую миграцию: column "user_uuid" of relation "orders" contains null values — БД не знает, чем заполнить поле для старых строк.

Эталонный паттерн для добавления NOT NULL-колонки на непустую таблицу — три отдельные миграции:

№ФайлЧто делает
00003add_user_uuid_column_to_orders.sqlADD COLUMN user_uuid UUID (NULL-able) — безопасно для существующих строк, у них просто будет NULL.
00004backfill_user_uuid_in_orders.sqlUPDATE orders SET user_uuid = '<плейсхолдер>' WHERE user_uuid IS NULL — заполняем старые строки. На реальном проде здесь должен быть запрос к источнику правды (аудит-лог, отдельная таблица), а в учебном проекте используем «системный» нулевой UUID.
00005set_user_uuid_not_null_in_orders.sqlALTER COLUMN user_uuid SET NOT NULL — включаем ограничение. К этому моменту все строки заполнены, и code уже всегда пишет user_uuid в новых INSERT'ах.

Почему отдельные файлы, а не одна миграция с тремя SQL-выражениями: каждый файл — атомарный шаг, который можно откатить независимо (goose down). Если в проде что-то пошло не так на шаге backfill, не нужно откатывать ADD COLUMN. Плюс на больших таблицах backfill можно вынести в отдельный деплой между шагом 1 и шагом 3, не блокируя выкатку.

Топики Kafka ​

Конвенция именования: <service>.<event-type> ​

Каждый топик содержит один тип события. Имя строится по шаблону <сервис-producer>.<тип-события>:

ТопикСобытиеProducerConsumer (Group ID)Ключ (Key)
order.paidOrderPaidOrderServiceAssemblyService (assembly-service)order_uuid
assembly.ship-assembledShipAssembledAssemblyServiceOrderService (order-service)order_uuid

Почему не order-events? Общий топик вроде order-events провоцирует складывать туда разные типы событий (OrderPaid, OrderCancelled, OrderCreated...). Consumer'у придётся фильтровать лишнее. Один топик = один тип события — проще, чище, каждый consumer подписывается ровно на то, что ему нужно.

Зачем разные consumer groups?

Каждый consumer group получает все сообщения из топика независимо. Это позволяет нескольким сервисам обрабатывать одни и те же события параллельно.

Создание топиков ​

В docker-compose включен KAFKA_AUTO_CREATE_TOPICS_ENABLE: "true" — топик создаётся автоматически при первом обращении producer'а или consumer'а. Имена топиков задаются в конфигурации каждого сервиса (config.local.yaml).

Зачем ключ order_uuid?

Kafka распределяет сообщения по партициям на основе ключа (Key). Алгоритм по умолчанию: hash(key) % num_partitions. Все события по одному заказу гарантированно попадут в одну партицию → порядок обработки сохраняется.

Без ключа (Key = nil) Kafka распределяет сообщения round-robin — события одного заказа могут оказаться в разных партициях, и при нескольких consumer'ах порядок обработки сломается.

Сейчас у нас 1 партиция на топик, поэтому ключ функционально не влияет. Но это best practice — указывать ключ всегда: стоит ноль усилий, а когда кто-то добавит партиции — всё продолжит работать корректно. Плюс ключ удобен для отладки в Kafka UI и необходим для log compaction.

go
// Ключ задаётся в поле Key при отправке сообщения:
err := h.producer.Send(ctx, &kafka.Message{
    Key:   []byte(order.UUID.String()),  // ← ключ партиционирования (uuid.UUID → string)
    Value: data,                          // сериализованный protobuf
})

Часть 4: AssemblyService (новый сервис) ​

AssemblyService эмулирует сборку корабля. У него нет внешнего API — он работает только через Kafka:

  1. Получает событие OrderPaid из топика order.paid
  2. Эмулирует сборку (случайная задержка 5–15 секунд)
  3. Отправляет событие ShipAssembled в топик assembly.ship-assembled

Обработка ошибок в Consumer

  • Ошибка десериализации → логируем, возвращаем nil (commit offset). Повторная попытка бессмысленна — данные не изменятся.
  • Ошибка отправки в Kafka → возвращаем error (НЕ commit). Сообщение будет переобработано.
  • Graceful Shutdown → возвращаем ctx.Err(). Сообщение НЕ коммитится, будет переобработано при следующем запуске.

Consumer нужно запускать в отдельной горутине и корректно останавливать при SIGTERM — через отмену контекста. Используйте тот же closer, что и для gRPC-серверов.

Часть 5: Изменения в OrderService ​

Обновлённый метод Pay ​

На неделе 4 метод Pay уже работал в транзакции: читал заказ → вызывал PaymentService → обновлял статус. Теперь нужно добавить в эту же транзакцию два новых действия: SELECT FOR UPDATE (блокировка заказа, подробнее — в Части 7) и отправку события OrderPaid в Kafka.

6pjm2o

Всё в одной транзакции — учебное упрощение

Мы сознательно делаем два сетевых вызова (gRPC + Kafka) внутри открытой транзакции с FOR UPDATE. Это плохая практика для продакшена, но допустимо в учебных целях.

Проблемы этого подхода:

  1. Долгая блокировка — транзакция держит FOR UPDATE лок на строке заказа, пока не завершатся оба сетевых вызова. Если PaymentService тормозит — все параллельные запросы на этот заказ висят.

  2. Неоткатываемость gRPC — если Kafka недоступен и мы делаем ROLLBACK, то gRPC-вызов к PaymentService уже выполнился: деньги списаны, а статус не обновился. Откатить сетевой вызов невозможно — БД ничего не знает о внешних системах.

  3. Фантомная отправка в Kafka — если produce прошёл успешно, но COMMIT упал, событие уже в Kafka, а в БД статус не изменился. OrderService думает, что оплата не прошла, а AssemblyService уже начинает сборку.

Как делают в продакшене: используют Outbox Pattern — вместо прямых сетевых вызовов, в транзакции сохраняются только намерения: запись в таблицу outbox (событие для Kafka) и/или запись-задание на вызов внешнего сервиса. Отдельный процесс (relay) читает outbox и выполняет побочные эффекты: публикует события в Kafka, вызывает gRPC-клиенты и т.д. В нашем случае relay бы и PaymentService вызывал, и событие OrderPaid в Kafka отправлял. Это гарантирует атомарность: либо и статус обновился, и намерения записаны — либо ничего.

В рамках ДЗ этот подход допустим — PaymentService и Kafka локальные и всегда доступны. Главное — понимать ограничения.

Kafka Consumer — событие ShipAssembled ​

OrderService слушает топик assembly.ship-assembled. При получении события ShipAssembled сервис должен:

  1. Десериализовать событие из protobuf
  2. Получить заказ из БД и проверить статус
  3. Если заказ уже ASSEMBLED — пропустить (идемпотентность, at-least-once семантика)
  4. Вызвать CommitParts через gRPC-клиент InventoryService
  5. Обновить статус заказа на ASSEMBLED

Идемпотентность

При at-least-once семантике одно и то же сообщение может прийти дважды. Проверка текущего статуса заказа предотвращает повторную обработку — никакой отдельной таблицы дедупликации не нужно.

Часть 7: SELECT FOR UPDATE — пессимистичные блокировки ​

На неделе 4 мы реализовали ReserveParts, ReleaseParts и Pay с использованием транзакций. Однако без блокировок два одновременных запроса могут вызвать race condition — например, зарезервировать одну и ту же последнюю деталь.

Проблема: race condition без блокировок ​

domjwe

Решение: SELECT FOR UPDATE ​

SELECT FOR UPDATE блокирует строки до конца транзакции. Второй запрос ждёт, пока первая транзакция завершится:

ebmsj

Важно

SELECT FOR UPDATE работает только внутри транзакции. Без BEGIN...COMMIT блокировка снимается сразу после SELECT — и от неё нет толку.

Где добавить блокировки ​

InventoryService — добавьте метод ListForUpdate в репозиторий. Это аналог List, но с FOR UPDATE и ORDER BY uuid в конце запроса. Замените вызов List на ListForUpdate в ReserveParts, ReleaseParts и CommitParts.

OrderService — добавьте метод GetForUpdate в репозиторий заказов. Замените Get на GetForUpdate в методах Pay и Cancel.

Почему ORDER BY важен при FOR UPDATE ​

Когда SELECT FOR UPDATE блокирует несколько строк, порядок блокировки имеет значение. Без ORDER BY PostgreSQL может возвращать строки в произвольном порядке — и два параллельных запроса могут заблокировать строки в разной последовательности, что приводит к deadlock:

era4qz

PostgreSQL обнаружит deadlock и принудительно откатит одну из транзакций с ошибкой. Приложение получит ошибку вместо результата.

ORDER BY uuid гарантирует, что все транзакции блокируют строки в одном и том же порядке. Если обе транзакции сначала берут engine-1, потом hull-1 — вторая просто подождёт на первой строке, а не создаст циклическую зависимость.

Для OrderService это неактуально

GetForUpdate блокирует одну строку (конкретный заказ по UUID), поэтому deadlock невозможен. ORDER BY нужен только в InventoryService, где ListForUpdate блокирует несколько деталей одновременно.

Тесты конкурентности ​

В boilerplate tests/api_test.go уже есть два теста, которые проверяют корректность блокировок:

  • TestInventory_ReserveParts_Concurrent_LastPart — два одновременных Reserve на последнюю деталь (stock=1): один успех, второй FailedPrecondition.
  • TestOrder_Pay_Concurrent_SameOrder — два одновременных Pay одного заказа: один 200, второй 409.

Без SELECT FOR UPDATE оба теста падают (race condition). С блокировкой — оба зелёные. Прогон тестов — обязательная часть приёмки задания.

Чего НЕ нужно делать ​

Почему так?

На этой неделе мы фокусируемся на Kafka и асинхронной коммуникации. Другие аспекты придут позже.

Kafka — упрощаем ​

Типичные ошибки

  • ❌ Не реализуйте Outbox Pattern — мы осознанно упрощаем, отправляя в Kafka прямо из транзакции
  • ❌ Не реализуйте exactly-once — работаем с at-least-once + идемпотентность через проверку статуса
  • ❌ Не используйте Kafka Streams — работаем с обычным consumer/producer
  • ❌ Не настраивайте несколько партиций — одна партиция на топик для простоты
  • ❌ Не создавайте Dead Letter Queue — ошибочные сообщения логируем и пропускаем

Инфраструктура — НЕ сейчас ​

Типичные ошибки

  • ❌ Не контейнеризируйте сервисы — Docker только для инфраструктуры (БД, Kafka)
  • ❌ Не добавляйте Redis — это неделя 6
  • ❌ Не добавляйте авторизацию — это неделя 6
  • ❌ Не добавляйте метрики/трейсы — это неделя 7

Бизнес-логика — не забегаем вперёд ​

Типичные ошибки

  • ❌ Не делайте retry с exponential backoff в producer — простой retry достаточен
  • ❌ Не реализуйте событие OrderCancelled в Kafka — отмена работает синхронно через gRPC
  • ❌ Не добавляйте новые HTTP-эндпоинты — API без изменений

CI Pipeline ​

В проекте настроен GitHub Actions CI, который автоматически запускается при создании PR. CI поднимает PostgreSQL и Redpanda через testcontainers прямо из тестов.

CI проверяет:

  • task lint — код проходит линтер
  • task test:coverage — unit-тесты с проверкой покрытия ≥40%
  • task test:api — API-тесты с реальной PostgreSQL и in-memory Kafka
  • task test:e2e — сквозные тесты order с реальной Kafka (Redpanda) через testcontainers

Требование

CI pipeline должен быть зелёным — это обязательное условие для принятия PR.

Заготовка CI

В заготовке homeworks/week_5/boilerplates/.github/workflows/ уже лежат test-e2e.yml и обновлённый ci.yml. Скопируйте их к себе поверх — старый ci.yml нужно перетереть, чтобы появился новый job test-e2e.

Контракт: CommitParts (InventoryService)

gRPC-метод: CommitParts ​

Назначение: Списание деталей со склада после успешной сборки корабля.

Когда вызывается: OrderService вызывает CommitParts после получения события ShipAssembled из Kafka.

ПолеТипОписание

Пустой ответ (успех = нет ошибки).

UPDATE parts
SET stock_quantity = stock_quantity - 1,
    reserved = reserved - 1
WHERE uuid = ANY($1)
  AND stock_quantity > 0
  AND reserved > 0
