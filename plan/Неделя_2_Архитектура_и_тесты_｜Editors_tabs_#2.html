Требование: ОДИН Pull Request ​

Обязательное требование

Домашнее задание сдаётся строго в ОДНОМ PR, содержащем:

  1. Рефакторинг архитектуры (разделение на слои)
  2. Unit-тесты для service слоя
  3. Покрытие тестами ≥40%

Это не прихоть — так ментору проще проверять, когда архитектура и тесты в одном PR. Рефакторинг без тестов бессмыслен, тесты без слоёв невозможны.

Требование: Русский язык ​

Обязательное требование

Весь пользовательский текст в коде должен быть на русском языке:

  • Тексты ошибок (errors.New("..."))
  • Сообщения логов (slog.Info("..."))
  • Комментарии в коде
  • Имена тест-кейсов в t.Run("...")
  • Wrapping-сообщения в fmt.Errorf("...")

Исключения — имена функций, переменных, пакетов, JSON-теги, HTTP-пути и другие технические идентификаторы остаются на английском.

Шаг 2: Правила зависимостей ​

d2eyi7

Важно

  • Зависимости направлены внутрь — от адаптеров к бизнес-логике
  • Service слой НЕ знает о конкретных реализациях репозиториев и клиентов
  • Service слой работает только через интерфейсы

Шаг 3: Модели данных на каждом слое ​

Каждый слой работает со своей моделью данных. Не используйте proto-типы в сервисном слое и доменные модели в репозитории напрямую.

8eorrf

Три модели данных

  • Proto / DTO (*inventoryv1.Part, orderv1.CreateOrderRequest) — сгенерированные типы из proto/OpenAPI. Живут только в API слое и client слое.
  • Model (model.Part, model.Order) — доменные типы с бизнес-семантикой. Enum-ы как типизированные строки (OrderStatus, PartType). Используются в service слое.
  • Record (record.Part, record.Order) — типы хранилища. Примитивные типы: Status string (не enum), PaymentMethod *string (не *PaymentMethod). Живут только в repository слое.

Между слоями — конвертеры:

  • internal/converter/ — Proto ↔ Model (для API слоя)
  • internal/repository/converter/ — Model ↔ Record (для Repository слоя)
  • internal/client/grpc/.../converter/ — Proto ↔ Model (для Client слоя)

Типичная ошибка

Не используйте model.Order напрямую как значение в map репозитория. Репозиторий должен хранить record.Order и конвертировать при записи/чтении. Даже если сейчас это in-memory — паттерн готовит вас к PostgreSQL в следующих неделях.

Шаг 4: Валидация — в сервисном слое ​

Валидация входных данных (формат UUID, допустимость enum-а) — это бизнес-логика, её место в service слое. Репозиторий доверяет данным, которые получает от сервиса.

go
// ✅ Сервис валидирует и передаёт распарсенный UUID в репозиторий
func (s *service) Get(ctx context.Context, id string) (model.Part, error) {
    parsed, err := uuid.Parse(id)
    if err != nil {
        return model.Part{}, errs.ErrInvalidUUID
    }
    return s.partRepo.Get(ctx, parsed) // uuid.UUID, не string
}

// ✅ Репозиторий принимает uuid.UUID — парсинг не нужен
func (r *repository) Get(ctx context.Context, id uuid.UUID) (model.Part, error) {
    rec, ok := r.parts[id]  // прямой lookup, без MustParse
    ...
}

Часть 2: Определение интерфейсов ​

Принцип инверсии зависимостей (DIP) ​

Интерфейсы определяются в пакете, который их использует, а не в том, который их реализует.

f5cw28

Сервис не импортирует репозиторий — он знает только свой интерфейс из deps.go. Репозиторий подставляется снаружи через функция New().

Пример: интерфейс репозитория ​

go
package order

import (
    "context"
    "sync"

    "your-project/order/internal/model"
)

type repository struct {
    mu     sync.RWMutex
    orders map[string]model.Order
}

// New создаёт новый in-memory репозиторий заказов.
func New() *repository {
    return &repository{
        orders: make(map[string]model.Order),
    }
}

func (r *repository) Create(ctx context.Context, order model.Order) error {
    r.mu.Lock()
    defer r.mu.Unlock()

    r.orders[order.UUID] = order
    return nil
}

func (r *repository) Get(ctx context.Context, uuid string) (model.Order, error) {
    r.mu.RLock()
    defer r.mu.RUnlock()

    order, ok := r.orders[uuid]
    if !ok {
        return model.Order{}, errs.ErrOrderNotFound
    }
    return order, nil
}

func (r *repository) Update(ctx context.Context, order model.Order) error {
    r.mu.Lock()
    defer r.mu.Unlock()

    if _, ok := r.orders[order.UUID]; !ok {
        return errs.ErrOrderNotFound
    }
    r.orders[order.UUID] = order
    return nil
}

Пример: интерфейс gRPC клиента ​

go
package v1

import (
    "context"
    "fmt"

    "google.golang.org/grpc/codes"
    "google.golang.org/grpc/status"

    "your-project/order/internal/client/grpc/inventory/v1/converter"
    inventoryv1 "your-project/shared/pkg/proto/inventory/v1"
)

type client struct {
    inventoryClient inventoryv1.InventoryServiceClient
}

// New создаёт обёртку над gRPC клиентом InventoryService.
func New(c inventoryv1.InventoryServiceClient) *client {
    return &client{inventoryClient: c}
}

func (c *client) ListParts(ctx context.Context, uuids []string) ([]model.Part, error) {
    resp, err := c.inventoryClient.ListParts(ctx, &inventoryv1.ListPartsRequest{
        Uuids: uuids,
    })
    if err != nil {
        st, ok := status.FromError(err)
        if ok && st.Code() == codes.NotFound {
            return nil, errs.ErrPartNotFound
        }
        return nil, fmt.Errorf("получить список деталей: %w", err)
    }

    return converter.PartsToModel(resp.GetParts()), nil
}

package errs

Wrapping ошибок ​

Правила по слоям ​

Репозиторий — если метод выполняет одну операцию, ошибка возвращается как есть (имя метода уже даёт контекст). Sentinel-ы возвращаются напрямую. Обёртка через fmt.Errorf нужна только когда в методе несколько шагов и без контекста не разберёшь, какой упал:

go
// Один шаг — возвращаем ошибку как есть
func (r *repository) Get(ctx context.Context, uuid string) (model.Order, error) {
    order, ok := r.orders[uuid]
    if !ok {
        return model.Order{}, errs.ErrOrderNotFound
    }
    return order, nil
}

Сервис — оборачивает ошибки от зависимостей через fmt.Errorf("глагол-инфинитив: %w", err). Формат обёртки: глагол в инфинитиве + существительное, без "не удалось", "ошибка при" и т.п.:

// internal/service/order/create.go
func (s *service) Create(ctx context.Context, req model.CreateOrderRequest) (model.Order, error) {
    parts, err := s.inventoryClient.ListParts(ctx, req.PartUUIDs())
    if err != nil {
        return model.Order{}, fmt.Errorf("получить детали: %w", err)
    }

    for _, part := range parts {
        if part.StockQuantity <= 0 {
            return model.Order{}, errs.ErrOutOfStock
        }
    }

    // ...
}

Антипаттерны ​

  • fmt.Errorf("валидация uuid: %w", errs.ErrInvalidUUID) — обёртка sentinel-а без реального контекста (sentinel уже говорит "неверный формат UUID")
  • if errors.Is(err, errs.ErrX) { return errs.ErrX } — бессмысленное пере-оборачивание (sentinel уже в цепочке)
  • "получение заказа из репозитория" — отглагольное существительное + "из ..." (правильно: "получить заказ")
  • "не удалось получить заказ" — "не удалось" избыточно, это и так ошибка (правильно: "получить заказ")

Проверка ошибок ​

В service слое достаточно оборачивать ошибки через %w — вызывающий код сможет распознать исходную ошибку через errors.Is, потому что он проходит по всей цепочке:

go
// internal/service/order/get.go
func (s *service) Get(ctx context.Context, uuid string) (model.Order, error) {
    order, err := s.orderRepo.Get(ctx, uuid)
    if err != nil {
        return model.Order{}, fmt.Errorf("получить заказ: %w", err)
    }
    return order, nil
}

Преобразование в HTTP/gRPC коды ошибок ​

В API слое преобразуйте доменные ошибки в коды протокола.

Для HTTP (ogen) ​

go
// internal/api/order/v1/get.go
func (a *api) GetOrder(ctx context.Context, params ogen.GetOrderParams) (*ogen.Order, error) {
    order, err := a.orderService.Get(ctx, params.OrderUUID.String())
    if err != nil {
        if errors.Is(err, errs.ErrOrderNotFound) {
            return nil, ogen.ErrNotFound // HTTP 404
        }
        if errors.Is(err, errs.ErrInvalidUUID) {
            return nil, ogen.ErrBadRequest // HTTP 400
        }
        return nil, err // HTTP 500
    }

    return converter.OrderToProto(order), nil
}

// internal/api/inventory/v1/get.go
func (a *api) GetPart(ctx context.Context, req *inventoryv1.GetPartRequest) (*inventoryv1.GetPartResponse, error) {
    part, err := a.partService.Get(ctx, req.GetUuid())
    if err != nil {

    return &inventoryv1.GetPartResponse{
        Part: converter.PartToProto(part),
    }, nil
}

Часть 5: Написание тестов ​

Требования к тестам ​

  1. Тесты ДОЛЖНЫ быть параллельными — t.Parallel() на уровне TestCreate и внутри каждого t.Run().
  2. Использовать Table-Driven подход — все кейсы описаны в слайсе структур, итерация через for range + t.Run().
  3. Моки создавать внутри каждого подтеста — это гарантирует изоляцию. НЕ используем Suite — он хранит моки в полях структуры, что вызывает data race при параллельном запуске подтестов.
  4. require для gates, assert для checks:
    • require.* — останавливает текущий подтест (t.Run) немедленно через t.FailNow(). Остальные подтесты продолжат работу. Используем для предусловий: если err != nil, дальнейшие проверки бессмысленны (будет nil-pointer panic).
    • assert.* — продолжает выполнение подтеста, собирая все ошибки. Используем для проверки конкретных значений: если одно поле неверное, хотим увидеть ВСЕ расхождения.

Пример: Parallel Table-Driven Test ​

go
// internal/service/order/create_test.go
package order

import (
    "context"
    "testing"

    "github.com/brianvoe/gofakeit/v7"
    "github.com/stretchr/testify/assert"
    "github.com/stretchr/testify/mock"
    "github.com/stretchr/testify/require"

    errs "your-project/order/internal/errors"
    "your-project/order/internal/model"
    "your-project/order/internal/service/order/mocks"
)

func TestCreate(t *testing.T) {
    t.Parallel()

    type args struct {
        req model.CreateOrderRequest
    }

    type expected struct {
        err           error
        wantOrderUUID bool // Ожидаем ли непустой UUID в ответе.
    }

    var (
        ctx = context.Background()

        hullUUID   = gofakeit.UUID()
        engineUUID = gofakeit.UUID()

        partsInStock = []model.Part{
            {UUID: hullUUID, Name: "Hull", Price: 500000, StockQuantity: 10},
            {UUID: engineUUID, Name: "Engine", Price: 300000, StockQuantity: 5},
        }

        partsOutOfStock = []model.Part{
            {UUID: hullUUID, Name: "Hull", Price: 500000, StockQuantity: 10},
            {UUID: engineUUID, Name: "Engine", Price: 300000, StockQuantity: 0},
        }
    )

    tests := []struct {
        name      string
        args      args
        setupMock func(repo *mocks.OrderRepository, client *mocks.InventoryClient)
        expected  expected
    }{
        {
            name: "успешное создание заказа",
            args: args{
                req: model.CreateOrderRequest{
                    HullUUID:   hullUUID,
                    EngineUUID: engineUUID,
                },
            },
            setupMock: func(repo *mocks.OrderRepository, client *mocks.InventoryClient) {
                client.EXPECT().
                    ListParts(ctx, []string{hullUUID, engineUUID}).
                    Return(partsInStock, nil)

                repo.EXPECT().
                    Create(ctx, mock.MatchedBy(func(o model.Order) bool {
                        return o.HullUUID == hullUUID &&
                            o.EngineUUID == engineUUID &&
                            o.TotalPrice == 800000 && // 500000 + 300000
                            o.Status == model.OrderStatusPendingPayment
                    })).
                    Return(nil)
            },
            expected: expected{err: nil, wantOrderUUID: true},
        },
        {
            name: "деталь не найдена",
            args: args{
                req: model.CreateOrderRequest{
                    HullUUID:   hullUUID,
                    EngineUUID: engineUUID,
                },
            },
            setupMock: func(repo *mocks.OrderRepository, client *mocks.InventoryClient) {
                client.EXPECT().
                    ListParts(ctx, []string{hullUUID, engineUUID}).
                    Return(nil, errs.ErrPartNotFound)
            },
            expected: expected{err: errs.ErrPartNotFound, wantOrderUUID: false},
        },
        {
            name: "деталь закончилась на складе",
            args: args{
                req: model.CreateOrderRequest{
                    HullUUID:   hullUUID,
                    EngineUUID: engineUUID,
                },
            },
            setupMock: func(repo *mocks.OrderRepository, client *mocks.InventoryClient) {
                client.EXPECT().
                    ListParts(ctx, []string{hullUUID, engineUUID}).
                    Return(partsOutOfStock, nil)
            },
            expected: expected{err: errs.ErrOutOfStock, wantOrderUUID: false},
        },
    }

    for _, tc := range tests {
        t.Run(tc.name, func(t *testing.T) {
            t.Parallel()

            orderRepo := mocks.NewOrderRepository(t)
            inventoryClient := mocks.NewInventoryClient(t)
            paymentClient := mocks.NewPaymentClient(t)

            tc.setupMock(orderRepo, inventoryClient)

            svc := New(orderRepo, inventoryClient, paymentClient)
            order, err := svc.Create(ctx, tc.args.req)

            if tc.expected.err != nil {
                require.Error(t, err)
                assert.ErrorIs(t, err, tc.expected.err)
                assert.Empty(t, order.UUID)
            } else {
                require.NoError(t, err)
                assert.NotEmpty(t, order.UUID)
            }
        })
    }
}

Чего НЕ нужно делать ​

Почему так?

На этой неделе мы фокусируемся на архитектуре и unit-тестах. Другие аспекты придут позже.

Тестирование — service и API слои ​

Типичные ошибки

  • ❌ Конвертеры (converter/) — там нет логики, только маппинг полей
  • ❌ Repository слой — на этой неделе это in-memory map, а в будущем тесты репозитория — это уже интеграционные тесты (с БД), не unit-тесты

Инфраструктура — НЕ сейчас ​

Типичные ошибки

  • ❌ Базу данных — продолжаем использовать map в памяти
  • ❌ Интеграционные тесты — только unit-тесты с моками
  • ❌ Метрики/трейсы — это неделя 7
  • ❌ Авторизацию — это неделя 6

Архитектура — упрощаем ​

Типичные ошибки

  • ❌ Не делайте несколько реализаций интерфейсов
  • ❌ Не добавляйте middleware в service слой
  • ❌ Не создавайте фабрики для создания объектов

Зачем нужен pkg/app/ ​

В неделе 1 вся логика жила в pkg/ напрямую (например, pkg/service/service.go), потому что API-тесты OrderService запускают InventoryService и PaymentService через bufconn — и им нужен доступ к конструкторам этих сервисов. Папка internal/ из другого Go-модуля недоступна, поэтому точка входа должна быть в pkg/.

В неделе 2, после разделения на слои, вся логика уехала в internal/. Пакет pkg/app/ — это тонкая обёртка, которая:

  • Собирает зависимости (DI)
  • Регистрирует сервисы на gRPC-сервере (или возвращает HTTP-обработчик)
  • НЕ создаёт grpc.Server — это дело main (keepalive, reflection — инфраструктурные детали)
go
// pkg/app/app.go — минимальный API для переиспользования в тестах
func RegisterServices(grpcServer *grpc.Server) {
    repo := partrepo.New()
    svc := partsvc.New(repo)
    api := inventoryapi.New(svc)
    inventoryv1.RegisterInventoryServiceServer(grpcServer, api)
}

Требования к покрытию ​

Минимум 40% покрытия ​

Покрытие считается для пакетов internal/api/ и internal/service/.

Команда task test:coverage автоматически проверяет, что общее покрытие не ниже 40%. Если покрытие ниже порога, команда завершается с ошибкой. Чтобы перепроверить порог без повторного запуска тестов, используйте task coverage:check.

bash
task test:coverage

Как это работает?

Unit-тесты проверяют бизнес-логику service слоя, изолируя зависимости с помощью моков. task test:coverage запускает все тесты с подсчётом покрытия и автоматически проверяет, что порог ≥40% достигнут. API-тесты task test:api запускают все три сервиса в памяти — gRPC-серверы через bufconn (без реальных портов), HTTP-сервер через httptest — и проверяют корректность работы API.

CI Pipeline ​

Важно

В проекте настроен GitHub Actions CI, который автоматически запускается при создании PR.

CI проверяет:

  • task lint — код проходит линтер
  • task test:coverage — unit-тесты с проверкой покрытия ≥40%
  • task test:api — API-тесты

Требование

CI pipeline должен быть зелёным — это обязательное условие для принятия PR.

Ответственность:

  5. Начальный статус = PENDING_PAYMENT

Pay ​

  1. Заказ должен существовать
  2. Статус должен быть PENDING_PAYMENT
  3. После успешной оплаты: статус → PAID, сохраняем transaction_uuid и payment_method

Cancel ​

  1. Заказ должен существовать
  2. Статус должен быть PENDING_PAYMENT
  3. После отмены: статус → CANCELLED

Бизнес-правила ​

Get ​

  1. UUID должен быть валидным форматом UUID v4
  2. Возвращает деталь или ErrPartNotFound

List ​

  1. Если filter.UUIDs не пустой:

    • Возвращаются только запрошенные детали
    • Порядок соответствует порядку UUID в запросе
    • Если хотя бы один UUID не найден → ErrPartNotFound
    • filter.PartType игнорируется

  2. Если filter.UUIDs пустой:

    • filter.PartType == UNSPECIFIED → все детали
    • Конкретный тип → только детали этого типа
    • Результат сортируется по имени (алфавитный порядок)

Пример реализации ​

go
// internal/service/payment/pay.go
package payment

import (
    "context"
    "log/slog"

    "github.com/google/uuid"

    "your-project/payment/internal/model"
)

func (s *service) Pay(ctx context.Context, req model.PayRequest) (string, error) {
    // 1. Валидация order_uuid
    if req.OrderUUID == "" {
        return "", errs.ErrInvalidOrderUUID
    }
    if _, err := uuid.Parse(req.OrderUUID); err != nil {
        return "", errs.ErrInvalidOrderUUID
    }

    // 2. Валидация payment_method
    if !req.PaymentMethod.IsValid() {
        return "", errs.ErrInvalidPaymentMethod
    }

    // 3. Генерация transaction_uuid
    transactionUUID := uuid.New().String()

    // 4. Логирование
    slog.InfoContext(ctx, "оплата выполнена",
        "order_uuid", req.OrderUUID,
        "transaction_uuid", transactionUUID,
        "payment_method", req.PaymentMethod)

    return transactionUUID, nil
}
