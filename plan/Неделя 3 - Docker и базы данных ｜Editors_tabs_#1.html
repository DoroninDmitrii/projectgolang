Требование: Русский язык ​

Обязательное требование

Весь пользовательский текст в коде должен быть на русском языке:

  • Тексты ошибок (errors.New("..."))
  • Сообщения логов (slog.Info("..."))
  • Комментарии в коде
  • Имена тест-кейсов в t.Run("...")
  • Wrapping-сообщения в fmt.Errorf("...")

Исключения — имена функций, переменных, пакетов, JSON-теги, HTTP-пути, SQL-запросы и другие технические идентификаторы остаются на английском.

OrderService — таблицы orders и order_items ​

На неделе 2 заказ хранил UUID деталей прямо в таблице (hull_uuid, engine_uuid, ...). Теперь мы нормализуем структуру: заказ — отдельно, строки заказа — отдельно. Это даёт нам реальный кейс для Transaction Manager: создание заказа — это INSERT в orders + несколько INSERT в order_items, и эти операции должны быть атомарными.

sql
-- +goose Up
CREATE TABLE orders (
    uuid UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    total_price BIGINT NOT NULL DEFAULT 0,
    status VARCHAR(50) NOT NULL DEFAULT 'PENDING_PAYMENT',
    transaction_uuid UUID,
    payment_method VARCHAR(50),
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMP
);

-- +goose Down
DROP TABLE IF EXISTS orders;

Подключение Transaction Manager ​

Для управления транзакциями используем production-ready библиотеку go-transaction-manager. Она кладёт транзакцию в контекст, достаёт обратно, с поддержкой вложенных транзакций и нескольких драйверов.

Установка:

bash
go get github.com/avito-tech/go-transaction-manager/trm/v2
go get github.com/avito-tech/go-transaction-manager/drivers/pgxv5/v2
1
2

Два ключевых компонента:

КомпонентПакетНазначение
manager.Managertrm/v2/managerОткрывает транзакцию, вызывает функцию, коммитит/откатывает
trmpgx.CtxGetterdrivers/pgxv5/v2Извлекает pgx.Tx из контекста (или возвращает пул, если транзакции нет)

Репозитории используют CtxGetter для прозрачной работы с транзакциями:

go
import (
    "github.com/jackc/pgx/v5/pgxpool"
    trmpgx "github.com/avito-tech/go-transaction-manager/drivers/pgxv5/v2"
)

type repository struct {
    pool   *pgxpool.Pool
    getter *trmpgx.CtxGetter
}

func New(pool *pgxpool.Pool) *repository {
    return &repository{
        pool:   pool,
        getter: trmpgx.DefaultCtxGetter,
    }
}

Зачем CtxGetter?

CtxGetter заменяет ручной паттерн if tx := ExtractTx(ctx); tx != nil { return tx }; return r.pool. Библиотека делает это за нас — вам не нужно писать хелпер db(ctx) и хранить txKey в контексте вручную.

Пример метода репозитория ​

Вот как выглядит типичный метод — Create для OrderService. Остальные методы реализуйте по аналогии, опираясь на контракты в конце задания:

go
func (r *repository) Create(ctx context.Context, order model.Order) error {
    repoOrder := converter.ToRepoModel(order)

    const query = `
        INSERT INTO orders (uuid, hull_uuid, engine_uuid, shield_uuid, weapon_uuid, total_price, status, created_at)
        VALUES ($1, $2, $3, $4, $5, $6, $7, $8)`

    _, err := r.getter.DefaultTrOrDB(ctx, r.pool).Exec(ctx, query,
        repoOrder.UUID,
        repoOrder.HullUUID,
        repoOrder.EngineUUID,
        repoOrder.ShieldUUID,
        repoOrder.WeaponUUID,
        repoOrder.TotalPrice,
        repoOrder.Status,
        repoOrder.CreatedAt,
    )
    if err != nil {
        return err
    }

    return nil
}

Часть 5: Transaction Manager ​

Зачем нужен ​

Без Transaction Manager код сервисного слоя зависит от деталей реализации БД (начать транзакцию, закоммитить, откатить). Transaction Manager инкапсулирует эту логику:

p8wap

Инициализация в main.go ​

go
import (
    trmpgx "github.com/avito-tech/go-transaction-manager/drivers/pgxv5/v2"
    "github.com/avito-tech/go-transaction-manager/trm/v2/manager"
)

// Создаём Transaction Manager для pgx
txManager, err := manager.New(trmpgx.NewDefaultFactory(pool))
if err != nil {
    slog.Error("создание transaction manager", "error", err)
    os.Exit(1)
}

trmpgx.NewDefaultFactory(pool) — фабрика, которая умеет начинать транзакцию через pool.BeginTx. manager.New оборачивает её в менеджер с поддержкой BEGIN/COMMIT/ROLLBACK.

Использование в Service слое ​

В сервисном слое Transaction Manager используется через интерфейс:

go
// order/internal/service/order/deps.go
package order

import "context"

// TxManager определяет контракт для управления транзакциями.
// *manager.Manager из go-transaction-manager удовлетворяет этому интерфейсу.
type TxManager interface {
    Do(ctx context.Context, fn func(ctx context.Context) error) error
}

Почему интерфейс, а не конкретный тип?

Сервисный слой не должен зависеть от конкретной реализации транзакций. Интерфейс с единственным методом Do позволяет: (1) легко мокать в тестах, (2) менять реализацию без изменения бизнес-логики.

Пример использования:

go
// Абстрактный пример: перевод средств между счетами
err = s.txManager.Do(ctx, func(ctx context.Context) error {
    // Списываем с одного счёта
    if err := s.accountRepo.Debit(ctx, fromUUID, amount); err != nil {
        return err
    }

    // Зачисляем на другой счёт
    // Если здесь ошибка — первая операция тоже откатится
    if err := s.accountRepo.Credit(ctx, toUUID, amount); err != nil {
        return err
    }

    return nil
})

Важно

Не делайте внешние вызовы (gRPC, HTTP) внутри транзакции. Транзакция держит соединение с БД — долгий внешний вызов заблокирует его. Вызывайте внешние сервисы до или после транзакции.

Чего НЕ нужно делать ​

Почему так?

На этой неделе мы фокусируемся на PostgreSQL и паттерне Transaction Manager. Другие аспекты придут позже.

Инфраструктура — упрощаем ​

Типичные ошибки

  • ❌ Не контейнеризируйте сервисы — Docker только для БД, сервисы запускаем go run
  • ❌ Не пишите Dockerfile для сервисов — это усложнит разработку
  • ❌ Не добавляйте Redis — это неделя 6
  • ❌ Не добавляйте Kafka — это неделя 5

Код — НЕ сейчас ​

Типичные ошибки

  • ❌ Не выносите конфигурацию в env/yaml и не создавайте DI-контейнер — хардкодим DSN прямо в main.go (конфиги и DI — неделя 4)
  • ❌ Не используйте ORM (GORM, ent) — пишем чистый SQL с pgx
  • ❌ Не добавляйте SELECT FOR UPDATE — блокировки будут на неделе 4

Бизнес-логика — минимальные изменения ​

Типичные ошибки

  • ❌ Не меняйте API — эндпоинты и proto остаются теми же
  • ❌ Не меняйте клиентский слой — gRPC клиенты без изменений

Сервисный слой изменится минимально: добавляется зависимость на TxManager и OrderItemRepository, метод Create оборачивает запись в транзакцию.

pkg/app/ — не удаляйте

pkg/app/app.go из недели 2 нужно сохранить. Он используется API-тестами (order/tests/api_test.go) для сборки InventoryService и PaymentService через bufconn. Тесты из модуля order не могут импортировать internal/ других модулей — pkg/app/ решает эту проблему. Этот паттерн сохраняется во всех последующих неделях, включая неделю 4, когда появляется DI-контейнер.

CI Pipeline ​

Важно

В проекте настроен GitHub Actions CI, который автоматически запускается при создании PR. CI включает PostgreSQL через services: в workflow.

CI проверяет:

  • task lint — код проходит линтер
  • task test:coverage — unit-тесты с проверкой покрытия ≥40%
  • task test:api — API-тесты с реальной PostgreSQL

Требование

CI pipeline должен быть зелёным — это обязательное условие для принятия PR.

Nullable поля в PostgreSQL ​

Опциональные поля (shield_uuid, weapon_uuid) в PostgreSQL хранятся как NULL. В Go используйте указатели:

go
// Модель хранилища
type Order struct {
    ShieldUUID *string `db:"shield_uuid"`  // NULL → nil
    WeaponUUID *string `db:"weapon_uuid"`  // NULL → nil
}

// Конвертация: domain → repo
if order.ShieldUUID != "" {
    repo.ShieldUUID = &order.ShieldUUID
}

// Конвертация: repo → domain
if repo.ShieldUUID != nil {
    order.ShieldUUID = *repo.ShieldUUID
}

Не используйте fmt.Sprintf для SQL

Никогда не подставляйте значения через fmt.Sprintf — это SQL injection.

go
// НЕПРАВИЛЬНО — SQL injection!
query := fmt.Sprintf("SELECT * FROM orders WHERE uuid = '%s'", uuid)

// ПРАВИЛЬНО — параметризованный запрос
query := "SELECT * FROM orders WHERE uuid = $1"
row := r.getter.DefaultTrOrDB(ctx, r.pool).QueryRow(ctx, query, uuid)

Таблица order_items ​

Таблица order_items хранит снимок (snapshot) деталей на момент создания заказа. Это не дублирование данных из InventoryService, а осознанное решение:

  • Цена фиксируется — если завтра деталь подорожает, заказ сохранит цену на момент покупки
  • Автономность сервиса — OrderService показывает заказы без gRPC-вызовов в InventoryService. Если Inventory недоступен — заказы всё равно отображаются
  • Защита от удаления — если деталь снимут с производства и удалят из каталога, история заказов не пострадает

Пример batch insert через Squirrel ​

go
func (r *repository) Create(ctx context.Context, items []model.OrderItem) error {
	query := squirrel.Insert("order_items").
		Columns("uuid", "order_uuid", "part_uuid", "part_type", "price").
		PlaceholderFormat(squirrel.Dollar)

	for _, item := range items {
		query = query.Values(item.UUID, item.OrderUUID, item.PartUUID, item.PartType, item.Price)
	}

	sql, args, err := query.ToSql()
	if err != nil {
		return fmt.Errorf("build query: %w", err)
	}

	_, err = r.pool.Exec(ctx, sql, args...)
	if err != nil {
		return fmt.Errorf("insert order items: %w", err)
	}

	return nil
}
