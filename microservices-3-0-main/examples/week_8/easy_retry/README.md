# Retry -- клиентские повторные попытки для gRPC

Пример клиентского retry через `grpc-ecosystem/go-grpc-middleware/v2`. Сервер симулирует первые 2 сбоя (`Unavailable`), клиент автоматически повторяет запрос и получает ответ на 3-й попытке.

## Концепция

Retry -- базовый паттерн отказоустойчивости: клиент автоматически повторяет неудачные запросы вместо того, чтобы падать с ошибкой. Ключевые решения при реализации:

**Экспоненциальный backoff с jitter.** Задержка между попытками растёт: 100ms, 200ms, 400ms. Jitter (+-20%) добавляет случайный разброс, чтобы сотни клиентов не ретраили одновременно (thundering herd).

**Selective retry.** Повторять имеет смысл только транзиентные ошибки -- сервер перезапускается (`Unavailable`), перегружен (`ResourceExhausted`). Бизнес-ошибки (`InvalidArgument`, `NotFound`) ретраить бесполезно -- результат будет тем же.

**Идемпотентность.** Retry предполагает, что повторный запрос безопасен. Для мутирующих операций это нужно обеспечивать на стороне сервера (дедупликация, идемпотентный ключ).

## На что обратить внимание

| Что | Файл | Зачем |
|-----|------|-------|
| Конфигурация retry | `cmd/client/main.go:39-43` | `WithMax`, `WithBackoff`, `WithCodes` -- три параметра, определяющих поведение |
| Подключение через interceptor | `cmd/client/main.go:48` | Retry прозрачен для бизнес-кода -- одна строка при создании клиента |
| Симуляция сбоев с таймингами | `internal/api/api.go:46-63` | Атомарные счётчики + UnixNano показывают реальные задержки backoff в логах |
| Бизнес-ошибка не ретраится | `internal/api/api.go:70-72` | `InvalidArgument` возвращается сразу, без повторов |
| Per-call override | `tests/api_test.go` | Глобальные настройки можно переопределить для конкретного вызова через `grpcretry.WithMax(5)` |

## Как запустить

```bash
task run:server     # терминал 1
task run:client     # терминал 2 -- в логах сервера видны задержки backoff
task test:api       # тесты
```

