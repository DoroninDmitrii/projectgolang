# Week 1 — как это работает

Подробный разбор примеров недели: что делает каждый сервер, из какого контракта и какой командой генерируется код, что именно оказывается в сгенерированных файлах и как оно стыкуется с рукописным кодом.

Разбираем последовательно, по одному примеру. Сейчас в документе первый: **`grpc/`**. Остальные будут дописываться в конец по мере разбора.

---

# `grpc/` — базовый gRPC-сервер

## 1. Что делает этот сервер

Один gRPC-сервис `ufo.v1.UFOService` на `localhost:50051`, четыре метода — создать, прочитать, обновить и удалить наблюдение НЛО. Данные лежат в обычной `map` в памяти процесса: перезапустил — всё пропало.

Чего здесь нет намеренно: HTTP, интерцепторов, базы данных, конфигов, слоёв. Это фундамент — всё остальное в неделе наращивается поверх ровно этой конструкции. Если понятен этот пример, остальные читаются как «то же самое плюс одна новая штука».

Что стоит вынести из разбора:

- как proto-контракт превращается в Go-код и что конкретно в этом коде оказывается;
- как gRPC-сервер понимает, какой из ваших методов вызвать;
- почему в `Get` стоит `proto.Clone`, а не просто возврат указателя;
- зачем опциональные поля обёрнуты в `StringValue`/`BoolValue`/`Int32Value`.

## 2. Карта файлов

Весь пример — 13 файлов (не считая `bin/`, куда ставится тулинг, и `go.sum`).

```
grpc/
├── proto/
│   ├── buf.yaml                    ← руками   конфиг линтера proto
│   ├── buf.gen.yaml                ← руками   что и куда генерировать
│   └── ufo/v1/ufo.proto            ← руками   КОНТРАКТ, источник истины      129 строк
│
├── pkg/proto/ufo/v1/                          ← НЕ ТРОГАТЬ, генерируется
│   ├── ufo.pb.go                   ← protoc-gen-go         структуры        790 строк
│   └── ufo_grpc.pb.go              ← protoc-gen-go-grpc    клиент+сервер    249 строк
│
├── cmd/
│   ├── grpc_server/
│   │   ├── main.go                 ← руками   сервер + бизнес-логика        215 строк
│   │   └── api_test.go             ← руками   18 тестов на bufconn          472 строки
│   └── grpc_client/
│       └── main.go                 ← руками   демо-клиент                   221 строка
│
├── Taskfile.yaml                   ← руками   команды сборки и генерации
├── .golangci.yml                   ← руками   конфиг линтера Go
├── go.mod / go.sum                 ← руками / go
└── README.md                       ← руками
```

Считаем строки: руками написано около 700 строк живого Go-кода плюс 129 строк контракта. Сгенерировано — **1039 строк**, и их никто никогда не редактирует.

| Что | Файл | Кто создал | Как обновить |
|-----|------|-----------|--------------|
| Контракт | `proto/ufo/v1/ufo.proto` | вы | правите руками |
| Структуры сообщений | `pkg/proto/ufo/v1/ufo.pb.go` | `protoc-gen-go` | `task proto:gen` |
| Клиент и сервер gRPC | `pkg/proto/ufo/v1/ufo_grpc.pb.go` | `protoc-gen-go-grpc` | `task proto:gen` |
| Реализация сервиса | `cmd/grpc_server/main.go` | вы | правите руками |
| Демо-клиент | `cmd/grpc_client/main.go` | вы | правите руками |

Признак сгенерированного файла — шапка `// Code generated by ... DO NOT EDIT.` в первой строке. Правки в таких файлах затираются при следующем `task proto:gen`, потому что в `buf.gen.yaml` стоит `clean: true`.

## 3. Контракт: `proto/ufo/v1/ufo.proto`

Это единственный источник истины. Всё в `pkg/proto/` — производная от него.

### Шапка файла

```proto
syntax = "proto3";

// Package ufo.v1 содержит API для работы с наблюдениями НЛО
package ufo.v1;

import "google/protobuf/timestamp.proto";
import "google/protobuf/wrappers.proto";

option go_package = "github.com/olezhek28-courses/microservices-course-examples/examples/week_1/grpc/pkg/proto/ufo/v1;ufo_v1";
```

Три вещи, на которые это влияет:

**`package ufo.v1`** — пространство имён protobuf. Из него собирается полное имя метода, которое реально уходит по сети:

```
/ufo.v1.UFOService/Create
 └─────┘ └────────┘ └────┘
 package  service   rpc
```

Именно эту строку вы пишете в `grpcurl`, и именно она лежит в HTTP/2-заголовке `:path` каждого запроса. Переименуете `package` — сломаете всех клиентов.

**`option go_package`** — состоит из двух частей, разделённых точкой с запятой:
- до `;` — import path, по которому Go-код будет импортировать пакет;
- после `;` — имя Go-пакета, то самое `package ufo_v1` в шапке сгенерированных файлов.

Без второй части имя вывелось бы из последнего сегмента пути (`v1`), и все импорты выглядели бы как `v1.CreateRequest`.

**Импорты** `timestamp.proto` и `wrappers.proto` — это стандартные типы protobuf (Well-Known Types). Их не надо ниоткуда скачивать, они встроены в `protoc`/`buf` и в Go-библиотеку `google.golang.org/protobuf`.

### Сервис

```proto
// UFOService предоставляет API для работы с наблюдениями НЛО
service UFOService {
  // Create создает новое наблюдение НЛО
  rpc Create(CreateRequest) returns (CreateResponse);

  // Get возвращает наблюдение НЛО по идентификатору
  rpc Get(GetRequest) returns (GetResponse);

  // Update обновляет существующее наблюдение НЛО
  rpc Update(UpdateRequest) returns (UpdateResponse);

  // Delete выполняет мягкое удаление наблюдения НЛО
  rpc Delete(DeleteRequest) returns (DeleteResponse);
}
```

Все четыре RPC — **унарные**: один запрос, один ответ. Стримов в этом примере нет, поэтому в сгенерированном `ServiceDesc` поле `Streams` окажется пустым.

Каждый RPC принимает и возвращает **отдельное сообщение**, даже когда внутри одно поле или вообще ничего (`UpdateResponse {}`). Это не бюрократия: добавить поле в существующее сообщение можно без ломки клиентов, а поменять сигнатуру `rpc Get(string)` — нельзя, такого в proto3 просто нет.

### Модель данных

```
Sighting                          ← то, что хранится и отдаётся наружу
├── uuid          string
├── info          SightingInfo    ← «полезная» часть, приходит от клиента
│   ├── observed_at       Timestamp
│   ├── location          string          обязательное
│   ├── description       string          обязательное
│   ├── color             StringValue     опционально
│   ├── sound             BoolValue       опционально
│   └── duration_seconds  Int32Value      опционально
├── created_at    Timestamp        ← ставит сервер при создании
├── updated_at    Timestamp        ← ставит сервер при обновлении
└── deleted_at    Timestamp        ← ставит сервер при мягком удалении

SightingUpdateInfo                ← отдельное сообщение ТОЛЬКО для Update
├── observed_at       Timestamp
├── location          StringValue  ← здесь обёртка, хотя в SightingInfo был string
├── description       StringValue  ← и здесь тоже
├── color             StringValue
├── sound             BoolValue
└── duration_seconds  Int32Value
```

Заметьте разделение: `SightingInfo` — то, что присылает клиент, `Sighting` — то, что хранит сервер (info + служебные метки времени). Клиент физически не может подделать `created_at`, потому что в `CreateRequest` лежит только `info`.

### Зачем wrapper-типы

Вот главная идея контракта. Сравните одно и то же поле в двух сообщениях:

```proto
message SightingInfo {
  // location место наблюдения
  string location = 2;                          // голая строка
}

message SightingUpdateInfo {
  // location место наблюдения (опционально)
  google.protobuf.StringValue location = 2;     // обёртка
}
```

В proto3 у скалярных полей **нет состояния «не задано»**. Незаполненный `string` и явно переданная пустая строка на проводе выглядят одинаково, и в Go оба превратятся в `""`. Для создания это не проблема — там все поля обязательны. Для **частичного обновления** это фатально: сервер не сможет отличить «не трогай location» от «сотри location».

Wrapper-типы решают это тем, что превращают поле во вложенное сообщение. В Go получается указатель:

| В Go | Что означает |
|------|--------------|
| `Location == nil` | клиент это поле не присылал → не трогаем |
| `Location = &StringValue{Value: ""}` | клиент прислал пустую строку → записываем пустую строку |
| `Location = &StringValue{Value: "Москва"}` | записываем «Москва» |

В главе 9 будет видно, как `Update` этим пользуется буквально построчно.

Альтернатива — ключевое слово `optional` в proto3 (даёт тот же указатель в Go). Здесь выбраны обёртки; работает то же самое, разница в форме записи.

### Почему всё закомментировано

В `proto/buf.yaml` включены правила `COMMENT_*`:

```yaml
version: v2
lint:
  use:
    - STANDARD
    - COMMENT_ENUM
    - COMMENT_ENUM_VALUE
    - COMMENT_FIELD
    - COMMENT_MESSAGE
    - COMMENT_ONEOF
    - COMMENT_RPC
    - COMMENT_SERVICE
```

Комментарий обязателен над каждым сервисом, RPC, сообщением и полем. Это не пожелание: `task proto:gen` зависит от `proto:lint`, поэтому **добавили поле без комментария — генерация не запустится**. Заодно эти комментарии переезжают в сгенерированный Go-код и всплывают в подсказках IDE.

## 4. Генерация: одна команда и что за ней стоит

```bash
task proto:gen
```

### Цепочка зависимостей

Задача из [grpc/Taskfile.yaml](grpc/Taskfile.yaml) объявлена так:

```yaml
proto:gen:
  desc: "Генерирует Go-код из .proto"
  deps: [buf:install, proto:install-plugins, proto:format, proto:lint]
  dir: proto
  cmds:
    - '{{.BUF}} generate'
```

Разворачивается в:

```
buf:install             ставит buf в ./bin  (если ещё нет)
proto:install-plugins   ставит protoc-gen-go и protoc-gen-go-grpc в ./bin
proto:format            buf format -w       переформатирует .proto на месте
proto:lint              buf lint            падает, если нет комментария
   ↓
buf generate            собственно генерация, из директории proto/
```

У install-задач стоит `status: test -x {{.BUF}}` — повторно инструменты не переустанавливаются.

### Инструменты ставятся локально

```yaml
BUF_VERSION: '1.69.0'
PROTOC_GEN_GO_VERSION: 'v1.36.11'
PROTOC_GEN_GO_GRPC_VERSION: 'v1.6.1'
BIN_DIR: '{{.ROOT_DIR}}/bin'
```

```bash
GOBIN=./bin go install github.com/bufbuild/buf/cmd/buf@v1.69.0
GOBIN=./bin go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.36.11
GOBIN=./bin go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@v1.6.1
```

Всё в `./bin` внутри примера, ничего в системный `$GOPATH/bin`. Поэтому у всех, кто склонировал репозиторий, генерация даёт побайтово одинаковый результат — версии плагинов зафиксированы, а не «какие оказались на машине».

Обратите внимание: классический `protoc` здесь вообще не нужен. `buf` содержит собственный компилятор proto и вызывает плагины напрямую.

### `buf.gen.yaml` — куда складывать

```yaml
version: v2
# Удаляет сгенеренное ранее, то что находится в out каждого плагина.
clean: true

plugins:
  - local: ../bin/protoc-gen-go
    out: ../pkg/proto
    opt:
      - paths=source_relative
  - local: ../bin/protoc-gen-go-grpc
    out: ../pkg/proto
    opt:
      - paths=source_relative
```

Построчно:

- **`local: ../bin/protoc-gen-go`** — путь относительно `proto/` (задача выполняется с `dir: proto`), то есть `grpc/bin/protoc-gen-go`. Не `plugin:` из реестра, не глобальный бинарь — именно тот, что поставил `task setup`.
- **`out: ../pkg/proto`** — корень выходной директории, `grpc/pkg/proto`.
- **`clean: true`** — перед генерацией содержимое `out` стирается. Удалили сообщение из `.proto` — его Go-структура исчезнет, а не останется висеть.
- **`paths=source_relative`** — раскладывать выход по структуре **исходников**:

  ```
  proto/ufo/v1/ufo.proto  →  pkg/proto/ufo/v1/ufo.pb.go
        └──┬──┘                        └──┬──┘
       путь в proto/            тот же путь в pkg/proto/
  ```

  Без этой опции путь строился бы из `go_package`, и файл уехал бы в `pkg/proto/github.com/olezhek28-courses/.../pkg/proto/ufo/v1/`.

### Форматтер не трогает генератор

В задаче `format`:

```bash
find . -type f -name '*.go' ! -path '*/mocks/*' ! -path '*/pkg/proto/*' -exec gofumpt -extra -w {} +
```

`pkg/proto/` исключён специально. Сгенерированный код отформатирован генератором по своим правилам; пропусти его через `gofumpt` — и каждый прогон `task proto:gen` будет давать бесконечный diff.

## 5. Что сгенерировал `protoc-gen-go` — `ufo.pb.go`

790 строк. Читать целиком не нужно — там пять повторяющихся категорий.

### Структура на каждое сообщение

11 сообщений в `.proto` → 11 Go-структур. Вот `SightingInfo` как есть:

```go
// SightingInfo базовая информация о наблюдении НЛО
type SightingInfo struct {
	state protoimpl.MessageState `protogen:"open.v1"`
	// observed_at время наблюдения НЛО
	ObservedAt *timestamppb.Timestamp `protobuf:"bytes,1,opt,name=observed_at,json=observedAt,proto3" json:"observed_at,omitempty"`
	// location место наблюдения
	Location string `protobuf:"bytes,2,opt,name=location,proto3" json:"location,omitempty"`
	// description описание наблюдаемого объекта
	Description string `protobuf:"bytes,3,opt,name=description,proto3" json:"description,omitempty"`
	// color цвет объекта (опционально)
	Color *wrapperspb.StringValue `protobuf:"bytes,4,opt,name=color,proto3" json:"color,omitempty"`
	// sound признак наличия звука (опционально)
	Sound *wrapperspb.BoolValue `protobuf:"bytes,5,opt,name=sound,proto3" json:"sound,omitempty"`
	// duration_seconds продолжительность наблюдения в секундах (опционально)
	DurationSeconds *wrapperspb.Int32Value `protobuf:"bytes,6,opt,name=duration_seconds,json=durationSeconds,proto3" json:"duration_seconds,omitempty"`
	unknownFields protoimpl.UnknownFields
	sizeCache     protoimpl.SizeCache
}
```

Что здесь видно:

- **комментарии из `.proto` переехали один в один** — вот ради чего правила `COMMENT_*`;
- **`snake_case` → `CamelCase`**: `observed_at` → `ObservedAt`, `duration_seconds` → `DurationSeconds`;
- **тег `protobuf:"..."`** хранит номер поля (`2`), тип на проводе (`bytes`) и оригинальное имя. Именно номер, а не имя, определяет совместимость: переименовать поле безопасно, поменять номер — сломать всех;
- **тег `json:"..."`** — для `encoding/json`; в gRPC не используется, пригождается при HTTP-мостах;
- **служебные поля** `state`, `unknownFields`, `sizeCache` — внутренняя кухня runtime. `unknownFields` хранит поля, которых нет в вашей версии схемы: старый сервер получит запрос от нового клиента, не поймёт новое поле, но при пересылке дальше не потеряет его.

### Маппинг типов

| В `.proto` | В Go | Почему так |
|-----------|------|-----------|
| `string` | `string` | значение, «не задано» неотличимо от `""` |
| `int32` | `int32` | значение |
| `google.protobuf.Timestamp` | `*timestamppb.Timestamp` | сообщение → указатель, есть `nil` |
| `google.protobuf.StringValue` | `*wrapperspb.StringValue` | сообщение → указатель, есть `nil` |
| `google.protobuf.BoolValue` | `*wrapperspb.BoolValue` | то же |
| `google.protobuf.Int32Value` | `*wrapperspb.Int32Value` | то же |
| `SightingInfo` (своё сообщение) | `*SightingInfo` | то же |

Правило простое: **скаляр — значение, сообщение — указатель**. Отсюда и вся история с wrapper-типами из главы 3.

### Геттеры на каждое поле

```go
func (x *SightingInfo) GetLocation() string {
	if x != nil {
		return x.Location
	}
	return ""
}

func (x *SightingInfo) GetColor() *wrapperspb.StringValue {
	if x != nil {
		return x.Color
	}
	return nil
}
```

Геттер **nil-safe**: вызов на `nil`-указателе не паникует, а возвращает нулевое значение. Это позволяет писать цепочки без проверок:

```go
req.GetInfo().GetLocation()   // безопасно, даже если Info == nil
req.Info.Location             // паника, если Info == nil
```

Поэтому в `main.go` вы видите `req.GetUuid()`, а не `req.Uuid`.

### Служебные методы: интерфейс `proto.Message`

На каждую структуру генерируются пять методов:

```go
func (x *SightingInfo) Reset()                            { ... }
func (x *SightingInfo) String() string                    { ... }
func (*SightingInfo)   ProtoMessage()                     {}
func (x *SightingInfo) ProtoReflect() protoreflect.Message { ... }
func (*SightingInfo)   Descriptor() ([]byte, []int)       { ... }
```

Вместе они реализуют интерфейс `proto.Message`. Без него не работает **ничего** из библиотеки protobuf:

- `proto.Marshal` / `proto.Unmarshal` — сериализация, то есть сам gRPC;
- `proto.Clone` — глубокая копия (пригодится в главе 9);
- `proto.Equal`, слияние сообщений, обход полей через рефлексию.

Ключевой из них — `ProtoReflect()`. Через него runtime узнаёт структуру сообщения во время выполнения и не занимается разбором Go-тегов на каждый вызов.

### Сжатый дескриптор схемы

В конце файла:

```go
const file_ufo_v1_ufo_proto_rawDesc = "" + ...     // весь .proto в бинарном виде

var (
	file_ufo_v1_ufo_proto_rawDescOnce sync.Once
	file_ufo_v1_ufo_proto_rawDescData []byte
)

func file_ufo_v1_ufo_proto_rawDescGZIP() []byte { ... }
```

Это **весь ваш `.proto`, упакованный в бинарь**: имена сообщений, номера полей, типы, сервис с методами. Отсюда две практические вещи:

1. `reflection.Register(s)` в `main.go` отдаёт этот дескриптор по сети — поэтому `grpcurl` работает без файла `.proto` на руках;
2. по нему runtime строит `protoreflect`-описание при старте процесса (`func init()` в конце файла).

Никакой магии: схема физически лежит внутри вашего бинарника.

## 6. Что сгенерировал `protoc-gen-go-grpc` — `ufo_grpc.pb.go`

249 строк, и это самая полезная для понимания часть. Пять блоков.

### Блок 1: константы полных имён

```go
const (
	UFOService_Create_FullMethodName = "/ufo.v1.UFOService/Create"
	UFOService_Get_FullMethodName    = "/ufo.v1.UFOService/Get"
	UFOService_Update_FullMethodName = "/ufo.v1.UFOService/Update"
	UFOService_Delete_FullMethodName = "/ufo.v1.UFOService/Delete"
)
```

Собраны из `package` + `service` + `rpc` — ровно то, что обсуждали в главе 3. Эта строка уходит в HTTP/2-заголовок `:path`. По ней сервер на другом конце понимает, что вызывать.

### Блок 2: клиентская сторона

Интерфейс — публичный контракт для потребителя:

```go
type UFOServiceClient interface {
	// Create создает новое наблюдение НЛО
	Create(ctx context.Context, in *CreateRequest, opts ...grpc.CallOption) (*CreateResponse, error)
	Get(ctx context.Context, in *GetRequest, opts ...grpc.CallOption) (*GetResponse, error)
	Update(ctx context.Context, in *UpdateRequest, opts ...grpc.CallOption) (*UpdateResponse, error)
	Delete(ctx context.Context, in *DeleteRequest, opts ...grpc.CallOption) (*DeleteResponse, error)
}
```

Реализация приватная (`uFOServiceClient` с маленькой буквы), наружу торчит только конструктор:

```go
func NewUFOServiceClient(cc grpc.ClientConnInterface) UFOServiceClient {
	return &uFOServiceClient{cc}
}
```

А вот всё тело метода целиком — здесь видно, что клиент почти ничего не делает:

```go
func (c *uFOServiceClient) Create(ctx context.Context, in *CreateRequest, opts ...grpc.CallOption) (*CreateResponse, error) {
	cOpts := append([]grpc.CallOption{grpc.StaticMethod()}, opts...)
	out := new(CreateResponse)
	err := c.cc.Invoke(ctx, UFOService_Create_FullMethodName, in, out, cOpts...)
	if err != nil {
		return nil, err
	}
	return out, nil
}
```

Четыре строки полезной работы: завести пустой ответ, позвать `Invoke` с полным именем метода, вернуть. Вся сетевая механика — сериализация, HTTP/2, ретраи, балансировка — внутри `c.cc.Invoke`, то есть в самой библиотеке gRPC, а не в генерируемом коде.

То, что тип возвращается как **интерфейс** `UFOServiceClient`, а не структура — важно для тестов: в них подставляется мок, реализующий тот же интерфейс.

### Блок 3: серверная сторона

```go
type UFOServiceServer interface {
	Create(context.Context, *CreateRequest) (*CreateResponse, error)
	Get(context.Context, *GetRequest) (*GetResponse, error)
	Update(context.Context, *UpdateRequest) (*UpdateResponse, error)
	Delete(context.Context, *DeleteRequest) (*DeleteResponse, error)
	mustEmbedUnimplementedUFOServiceServer()
}
```

Обратите внимание на разницу с клиентским интерфейсом: нет `opts ...grpc.CallOption` (они клиентские) и есть непонятный пятый метод.

`mustEmbedUnimplementedUFOServiceServer()` — приватный метод (с маленькой буквы), поэтому реализовать его из вашего пакета **невозможно**. Единственный способ удовлетворить интерфейс — встроить готовую заглушку:

```go
type UnimplementedUFOServiceServer struct{}

func (UnimplementedUFOServiceServer) Create(context.Context, *CreateRequest) (*CreateResponse, error) {
	return nil, status.Error(codes.Unimplemented, "method Create not implemented")
}
// ... то же для Get, Update, Delete
func (UnimplementedUFOServiceServer) mustEmbedUnimplementedUFOServiceServer() {}
```

Именно поэтому в `main.go` написано так:

```go
type ufoService struct {
	ufov1.UnimplementedUFOServiceServer   // ← встроено по значению, не указателем

	mu        sync.RWMutex
	sightings map[string]*ufov1.Sighting
}
```

**Зачем это нужно — forward compatibility.** Добавили в `.proto` пятый RPC, перегенерировали, но реализацию ещё не написали:

- интерфейс `UFOServiceServer` вырос на один метод;
- ваша структура его не реализует — **но** встроенный `UnimplementedUFOServiceServer` реализует;
- код компилируется, сервер запускается, старые методы работают;
- вызов нового метода вернёт клиенту `codes.Unimplemented` вместо падения.

Без этой конструкции каждое расширение контракта ломало бы сборку всех сервисов сразу.

**Почему по значению, а не указателем** — в сгенерированном коде это прямо отмечено комментарием:

```go
// NOTE: this should be embedded by value instead of pointer to avoid a nil
// pointer dereference when methods are called.
```

Встроите указателем — он останется `nil`, и вызов нереализованного метода даст панику вместо аккуратного `Unimplemented`. `RegisterUFOServiceServer` проверяет это при старте:

```go
func RegisterUFOServiceServer(s grpc.ServiceRegistrar, srv UFOServiceServer) {
	if t, ok := srv.(interface{ testEmbeddedByValue() }); ok {
		t.testEmbeddedByValue()   // паникует сразу при регистрации, а не через месяц в проде
	}
	s.RegisterService(&UFOService_ServiceDesc, srv)
}
```

### Блок 4: диспетчер — функции `_Handler`

На каждый RPC генерируется функция-переходник. Вот она целиком:

```go
func _UFOService_Create_Handler(srv interface{}, ctx context.Context, dec func(interface{}) error, interceptor grpc.UnaryServerInterceptor) (interface{}, error) {
	in := new(CreateRequest)
	if err := dec(in); err != nil {       // ← распаковка тела запроса
		return nil, err
	}
	if interceptor == nil {
		return srv.(UFOServiceServer).Create(ctx, in)   // ← прямой вызов вашего метода
	}
	info := &grpc.UnaryServerInfo{
		Server:     srv,
		FullMethod: UFOService_Create_FullMethodName,
	}
	handler := func(ctx context.Context, req interface{}) (interface{}, error) {
		return srv.(UFOServiceServer).Create(ctx, req.(*CreateRequest))
	}
	return interceptor(ctx, in, info, handler)          // ← вызов через интерцептор
}
```

Что здесь происходит:

1. заводится пустой `CreateRequest`;
2. `dec(in)` — колбэк от gRPC-рантайма, внутри `proto.Unmarshal` тела запроса;
3. **если интерцепторов нет** — сразу вызывается ваш метод, ноль накладных расходов;
4. **если есть** — ваш метод заворачивается в замыкание `handler` и передаётся интерцептору вместе с `info`, где лежит полное имя метода.

Вот это место — стык, через который работают все интерцепторы. В следующем примере недели (`grpc_with_interceptor/`) сервер создаётся с `grpc.ChainUnaryInterceptor(...)`, и параметр `interceptor` здесь перестаёт быть `nil`. Никакой другой магии там нет — просто ветка `else` в этой функции.

Заодно понятно, откуда интерцептор берёт `info.FullMethod` для логов: его подставляет вот эта сгенерированная функция.

### Блок 5: `ServiceDesc` — таблица маршрутизации

```go
var UFOService_ServiceDesc = grpc.ServiceDesc{
	ServiceName: "ufo.v1.UFOService",
	HandlerType: (*UFOServiceServer)(nil),
	Methods: []grpc.MethodDesc{
		{MethodName: "Create", Handler: _UFOService_Create_Handler},
		{MethodName: "Get",    Handler: _UFOService_Get_Handler},
		{MethodName: "Update", Handler: _UFOService_Update_Handler},
		{MethodName: "Delete", Handler: _UFOService_Delete_Handler},
	},
	Streams:  []grpc.StreamDesc{},
	Metadata: "ufo/v1/ufo.proto",
}
```

Это и есть ответ на вопрос «как сервер понимает, что вызывать». Обычная таблица: имя сервиса, список методов, на каждый — указатель на `_Handler` из блока 4. `RegisterUFOServiceServer` кладёт её в `grpc.Server`, и дальше маршрутизация — это два поиска по строке из `:path`.

`Streams` пуст, потому что в контракте нет стриминговых RPC. `HandlerType` нужен для проверки типа при регистрации.

## 7. Сервер: `cmd/grpc_server/main.go`

Файл [grpc/cmd/grpc_server/main.go](grpc/cmd/grpc_server/main.go) содержит и запуск сервера, и саму реализацию сервиса — разделения на слои в этом примере ещё нет (оно появится в `workspace/`).

### Шаг 1: слушающий сокет

```go
lis, err := net.Listen("tcp", "localhost:50051")
if err != nil {
	slog.Error("ошибка запуска слушателя", "error", err)
	return
}
// Примечание: defer lis.Close() не нужен, так как GracefulStop() закрывает listener автоматически
```

Адрес `localhost:50051`, а не `:50051` — сервер доступен только с этой машины.

`defer lis.Close()` действительно не нужен: `GracefulStop()` закрывает listener сам. Написали бы — получили бы двойное закрытие и ошибку в логе на выходе.

### Шаг 2: сервер с настройками keepalive

```go
s := grpc.NewServer(
	grpc.KeepaliveParams(keepalive.ServerParameters{
		MaxConnectionIdle:     15 * time.Minute,
		MaxConnectionAge:      30 * time.Minute,
		MaxConnectionAgeGrace: 5 * time.Second,
		Time:                  5 * time.Minute,
		Timeout:               1 * time.Second,
	}),
	grpc.KeepaliveEnforcementPolicy(keepalive.EnforcementPolicy{
		MinTime:             5 * time.Minute,
		PermitWithoutStream: true,
	}),
)
```

| Параметр | Значение | Что делает |
|----------|----------|-----------|
| `MaxConnectionIdle` | 15 мин | закрыть соединение, если по нему 15 минут не было активных RPC |
| `MaxConnectionAge` | 30 мин | принудительно закрыть соединение через 30 минут жизни, даже активное |
| `MaxConnectionAgeGrace` | 5 сек | сколько дать на завершение текущих RPC после решения закрыть |
| `Time` | 5 мин | как часто слать ping для проверки живости |
| `Timeout` | 1 сек | сколько ждать pong, прежде чем считать соединение мёртвым |
| `MinTime` | 5 мин | минимальный интервал ping'ов **от клиента**; чаще — сервер отвечает `ENHANCE_YOUR_CALM` |
| `PermitWithoutStream` | `true` | разрешить клиенту пинговать без активных RPC, держа соединение «тёплым» |

Зачем `MaxConnectionAge` вообще нужен: gRPC мультиплексирует всё в одно долгоживущее TCP-соединение. Если его не ротировать, клиент, подключившийся к одному поду, останется на нём навсегда — новые поды не получат нагрузки. Принудительная ротация раз в 30 минут заставляет клиента переподключиться и перебалансироваться.

`MinTime` — защита: без него клиент мог бы пинговать сервер тысячу раз в секунду.

Подробный разбор каждого параметра, GOAWAY и жизненного цикла соединений — в [GRPC_CONNECTIONS.md](GRPC_CONNECTIONS.md).

### Шаг 3: регистрация сервиса

```go
service := &ufoService{
	sightings: make(map[string]*ufov1.Sighting),
}

ufov1.RegisterUFOServiceServer(s, service)
```

Именно здесь `UFOService_ServiceDesc` из главы 6 попадает внутрь `grpc.Server`. Инициализировать `mu sync.RWMutex` не нужно — нулевое значение мьютекса уже рабочее, а вот `make` для map обязателен: запись в `nil`-map паникует.

### Шаг 4: рефлексия

```go
reflection.Register(s)
```

Одна строка добавляет служебный сервис `grpc.reflection.v1.ServerReflection`, который отдаёт наружу дескриптор схемы из главы 5. Благодаря ей работает:

```bash
grpcurl -plaintext localhost:50051 list                 # список сервисов
grpcurl -plaintext localhost:50051 describe ufo.v1.UFOService
```

Без рефлексии пришлось бы каждый раз указывать `-proto proto/ufo/v1/ufo.proto -import-path proto`. В проде рефлексию обычно выключают — она раскрывает всё API сервиса.

### Шаг 5: запуск и ожидание сигнала

```go
ctx, cancel := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
defer cancel()

go func() {
	slog.Info("🚀 gRPC сервер запущен", "address", grpcAddress)
	if serveErr := s.Serve(lis); serveErr != nil {
		slog.Error("ошибка запуска сервера", "error", serveErr)
		cancel() // будим main, чтобы не висеть бесконечно
	}
}()

<-ctx.Done()
```

`signal.NotifyContext` даёт контекст, который сам отменяется по `SIGINT` (Ctrl+C) или `SIGTERM` (что шлёт Kubernetes при выкатке).

`s.Serve(lis)` блокирующий, поэтому уходит в горутину. Тонкость — `cancel()` внутри горутины: если `Serve` упал (например, порт занят), контекст отменяется вручную, и `main` не зависает навсегда на `<-ctx.Done()`.

### Шаг 6: graceful shutdown

```go
<-ctx.Done()
slog.Info("🛑 остановка gRPC сервера")
s.GracefulStop()
slog.Info("✅ сервер остановлен")
```

Разница принципиальная:

| | `GracefulStop()` | `Stop()` |
|---|---|---|
| Новые соединения | отклоняются | отклоняются |
| Текущие RPC | **дожидается завершения** | обрывает немедленно |
| Клиенты | получают ответы | получают `Unavailable` |
| Когда применять | прод, выкатка | тесты, аварийная остановка |

Именно `GracefulStop` делает деплой незаметным для пользователей: Kubernetes шлёт `SIGTERM`, сервер перестаёт принимать новое, доделывает начатое и выходит.

Главы 5, 6 и 7 соединяются вот здесь. Путь вызова `Create` от клиента до вашего кода и обратно:

        ▼ обратный путь

  HTTP/2 DATA + трейлер  grpc-status: 0

### Что меняется при ошибке

Ваш метод вернул ошибку вместо ответа:

```go
return nil, status.Errorf(codes.NotFound, "наблюдение с UUID %s не найдено", req.GetUuid())
```

Дальше:

1. gRPC не шлёт тело ответа вообще;
2. в трейлерах уходит `grpc-status: 5` (числовой код `NotFound`) и `grpc-message` с текстом;
3. на клиенте `Invoke` возвращает `error`, а `out` остаётся пустым;
4. разобрать код можно так:

```go
st, ok := status.FromError(err)
if ok && st.Code() == codes.NotFound {
	// ...
}
```

Важно: **обычная Go-ошибка тоже долетит**, но с кодом `Unknown`. Поэтому в сервисе везде `status.Error(codes.X, ...)`, а не `errors.New` — иначе клиент не сможет отличить «не найдено» от «сервер сломался».

Коды, которые использует этот сервис:

| Код | Номер | Когда |
|-----|-------|-------|
| `OK` | 0 | успех |
| `InvalidArgument` | 3 | пустой `uuid`, `info == nil`, `update_info == nil` |
| `NotFound` | 5 | нет записи с таким uuid |
| `Unimplemented` | 12 | метод есть в контракте, но не реализован (из `UnimplementedUFOServiceServer`) |

## 9. Бизнес-логика: четыре RPC

Хранилище — поля той же структуры, что реализует сервис:

```go
type ufoService struct {
	ufov1.UnimplementedUFOServiceServer

	mu        sync.RWMutex
	sightings map[string]*ufov1.Sighting
}
```

`RWMutex`, а не `Mutex`: читатели (`Get`) не блокируют друг друга, писатели (`Create`/`Update`/`Delete`) блокируют всех.

| RPC | Что делает | Ошибки |
|-----|-----------|--------|
| `Create` | генерирует uuid, ставит `CreatedAt`, кладёт в map, возвращает **только uuid** | `InvalidArgument` при `info == nil` |
| `Get` | читает под `RLock`, возвращает глубокую копию | `InvalidArgument` (пустой uuid), `NotFound` |
| `Update` | частичное обновление не-nil полей, ставит `UpdatedAt` | `InvalidArgument` (пустой uuid или `update_info == nil`), `NotFound` |
| `Delete` | мягкое удаление: ставит `DeletedAt` | `InvalidArgument`, `NotFound` |

Три места, ради которых стоит читать этот код.

### `proto.Clone` в `Get` — защита от гонки

```go
func (s *ufoService) Get(_ context.Context, req *ufov1.GetRequest) (*ufov1.GetResponse, error) {
	// ...
	s.mu.RLock()
	defer s.mu.RUnlock()

	sighting, ok := s.sightings[req.GetUuid()]
	if !ok {
		return nil, status.Errorf(codes.NotFound, "наблюдение с UUID %s не найдено", req.GetUuid())
	}

	// proto.Clone создаёт глубокую копию, чтобы клиент не получил указатель
	// на объект в хранилище — иначе gRPC может читать его параллельно с записью (data race)
	return &ufov1.GetResponse{
		Sighting: proto.Clone(sighting).(*ufov1.Sighting),
	}, nil
}
```

Почему нельзя вернуть указатель напрямую — из главы 8 видно порядок событий:

```
ваш Get:   RLock → читает map → return  → RUnlock (по defer)
                                            │
gRPC:                                       └→ proto.Marshal(ответ)   ← ЗДЕСЬ
```

`RUnlock` срабатывает при выходе из вашего метода, а сериализация происходит **позже**, уже в библиотеке gRPC. В этот момент параллельный `Update` спокойно берёт `Lock` и пишет в тот же самый объект, который сейчас сериализуется. Классический data race: `go test -race` его поймает, а в проде это редкий невоспроизводимый баг.

`proto.Clone` копирует всё дерево целиком, и наружу уходит объект, на который больше никто не ссылается.

### Частичное обновление в `Update`

Здесь окупаются wrapper-типы из главы 3:

```go
if req.GetUpdateInfo().ObservedAt != nil {
	sighting.Info.ObservedAt = req.GetUpdateInfo().ObservedAt
}

if req.GetUpdateInfo().Location != nil {
	sighting.Info.Location = req.GetUpdateInfo().Location.Value
}

if req.GetUpdateInfo().Description != nil {
	sighting.Info.Description = req.GetUpdateInfo().Description.Value
}

if req.GetUpdateInfo().Color != nil {
	sighting.Info.Color = req.GetUpdateInfo().Color
}
// ... Sound, DurationSeconds аналогично

sighting.UpdatedAt = timestamppb.New(time.Now())
```

Проверка `!= nil` — это и есть «клиент прислал это поле». Прислал только `color` — остальные пять полей останутся нетронутыми.

Тонкость в разнице двух веток:

- **`Location`** в хранилище — голый `string`, поэтому из обёртки достаётся `.Value`;
- **`Color`** в хранилище — уже `*StringValue`, поэтому указатель кладётся как есть.

То есть `SightingUpdateInfo` служит транспортом для «задано / не задано», а внутри `SightingInfo` часть полей разворачивается обратно в скаляры.

`UpdatedAt` ставится всегда, даже если клиент прислал пустой `update_info` со всеми `nil` — по факту вызова.

### Идемпотентное мягкое удаление

```go
sighting, ok := s.sightings[req.GetUuid()]
if !ok {
	return nil, status.Errorf(codes.NotFound, "наблюдение с UUID %s не найдено", req.GetUuid())
}

// Мягкое удаление - устанавливаем deleted_at (идемпотентно: не перезаписываем если уже удалено)
if sighting.DeletedAt == nil {
	sighting.DeletedAt = timestamppb.New(time.Now())
}
```

Записи из map **не удаляются**. Последствия, которые надо держать в голове:

- `Get` после `Delete` вернёт `200 OK` и объект с заполненным `deleted_at`, а не `NotFound` — фильтровать удалённые должен вызывающий;
- повторный `Delete` вернёт успех и не перезапишет `DeletedAt` — время первого удаления сохраняется;
- `Delete` несуществующего uuid — всё-таки `NotFound`.

Мягкое удаление — обычная практика: данные не теряются, история восстановима, а внешние ссылки на запись не превращаются в битые.

## 10. Клиент, тесты, запуск

### Демо-клиент

[grpc/cmd/grpc_client/main.go](grpc/cmd/grpc_client/main.go) прогоняет полный цикл: Create → Get → Update → Get → Delete → Get, печатая результат каждого шага.

```go
conn, err := grpc.NewClient(
	serverAddress,
	grpc.WithTransportCredentials(insecure.NewCredentials()),
	grpc.WithKeepaliveParams(keepalive.ClientParameters{
		Time:                10 * time.Second,
		Timeout:             3 * time.Second,
		PermitWithoutStream: true,
	}),
)
// ...
client := ufov1.NewUFOServiceClient(conn)
```

Что тут стоит отметить:

- **`grpc.NewClient`, а не `grpc.Dial`** — `Dial` устарел. `NewClient` не подключается сразу: он создаёт «ленивый» канал, который установит соединение при первом вызове и будет переподключаться сам. Поэтому клиент стартует, даже если сервер ещё не поднят.
- **`insecure.NewCredentials()`** — без TLS. Годится для локальной разработки; в проде — реальные креды.
- **Клиентский keepalive агрессивнее серверного**: `Time 10s` против `5m`. Формально это конфликтует с серверным `MinTime: 5m` — сервер вправе прислать `ENHANCE_YOUR_CALM` и закрыть соединение; для демо-клиента, живущего несколько секунд, это ни на что не влияет.

Опциональные поля собираются через хелперы:

```go
if gofakeit.Bool() {
	info.Color = wrapperspb.String(gofakeit.Color())
}
if gofakeit.Bool() {
	info.Sound = wrapperspb.Bool(gofakeit.Bool())
}
```

`wrapperspb.String("x")` — это просто `&wrapperspb.StringValue{Value: "x"}`. Каждое поле добавляется с вероятностью 50%, поэтому при каждом запуске форма запроса разная — заодно проверяется, что сервер корректно переживает `nil` в любом опциональном поле.

### Тесты

[grpc/cmd/grpc_server/api_test.go](grpc/cmd/grpc_server/api_test.go) — 18 тестов, покрывающих все четыре RPC, включая граничные случаи (`TestCreate_UniqueUUIDs`, `TestUpdate_SingleField`, `TestDelete_AlreadyDeleted`, `TestFullLifecycle`).

Сервер поднимается **в памяти, без TCP-порта**:

```go
const bufSize = 1024 * 1024

var (
	lis    *bufconn.Listener
	client ufov1.UFOServiceClient
)

func TestMain(m *testing.M) {
	lis = bufconn.Listen(bufSize)
	s := grpc.NewServer()

	service := &ufoService{
		sightings: make(map[string]*ufov1.Sighting),
	}
	ufov1.RegisterUFOServiceServer(s, service)

	go func() { ... s.Serve(lis) ... }()

	conn, err := grpc.NewClient(
		"passthrough:///bufnet",
		grpc.WithContextDialer(bufDialer),
		grpc.WithTransportCredentials(insecure.NewCredentials()),
	)
	client = ufov1.NewUFOServiceClient(conn)

	code := m.Run()

	conn.Close()
	s.Stop()
	os.Exit(code)
}

func bufDialer(context.Context, string) (net.Conn, error) {
	return lis.Dial()
}
```

`bufconn` подменяет транспорт: вместо TCP — буфер в памяти. `grpc.WithContextDialer(bufDialer)` заставляет клиент ходить туда, а `passthrough:///bufnet` отключает резолвер имён (адрес фиктивный, реального DNS-разрешения быть не должно).

Что это даёт: тесты не занимают порт `50051`, не конфликтуют при параллельном запуске и не зависят от состояния машины. При этом код проходит **настоящий** путь из главы 8 — сериализацию, `ServiceDesc`, `_Handler` — в отличие от прямого вызова методов сервиса.

Две детали, отличающие тестовый сервер от боевого: он создаётся как голый `grpc.NewServer()` — без keepalive-настроек, они здесь не нужны; и гасится через `s.Stop()`, а не `GracefulStop()` — тестам не нужно ждать завершения RPC.

Хелпер для проверки кодов ошибок:

```go
func assertGRPCStatus(t *testing.T, err error, expectedCode codes.Code) {
	t.Helper()
	if expectedCode == codes.OK {
		assert.NoError(t, err, "ожидалось отсутствие ошибки")
		return
	}
	require.Error(t, err, "ожидалась ошибка")
	// ... разбирает status.FromError и сверяет код
}
```

### Проверка через grpcurl

Работает благодаря `reflection.Register(s)` — файл `.proto` указывать не нужно:

```bash
# какие сервисы есть
grpcurl -plaintext localhost:50051 list

# какие методы у сервиса
grpcurl -plaintext localhost:50051 list ufo.v1.UFOService

# полное описание, включая поля сообщений
grpcurl -plaintext localhost:50051 describe ufo.v1.UFOService

# создать наблюдение
grpcurl -plaintext -d '{
  "info": {
    "location": "Roswell, New Mexico",
    "description": "Яркий диск над пустыней",
    "color": "silver"
  }
}' localhost:50051 ufo.v1.UFOService/Create

# прочитать по uuid из ответа выше
grpcurl -plaintext -d '{"uuid": "ВСТАВЬТЕ_UUID"}' \
  localhost:50051 ufo.v1.UFOService/Get
```

Обратите внимание на JSON-представление обёрток: `"color": "silver"`, а не `"color": {"value": "silver"}`. Так работает канонический JSON-маппинг protobuf для wrapper-типов.

### Порядок при изменении API

1. правите `proto/ufo/v1/ufo.proto` (не забыв комментарий к новому полю — иначе `buf lint` не пропустит);
2. `task proto:gen`;
3. компилятор показывает, что сломалось: новый метод в интерфейсе `UFOServiceServer`, изменившаяся сигнатура, переименованное поле;
4. дописываете бизнес-логику;
5. `task lint && task test:api`.

Направление всегда одно: **контракт → код**. Обратно не бывает — `pkg/proto/` переписывается заново на каждой генерации.
