# HTTP Chi + Ogen — contract-first API

Тот же Weather API, но с кодогенерацией из OpenAPI-спецификации через Ogen. Демонстрирует contract-first подход: сначала описываем API, потом генерируем код.

## Концепция

Contract-first — подход, при котором API описывается в формальной спецификации (OpenAPI YAML), а код сервера и клиента генерируется автоматически. Это гарантирует, что реализация всегда соответствует контракту.

Ogen генерирует из OpenAPI-спецификации:
- интерфейс `Handler`, который нужно реализовать
- типизированные структуры запросов/ответов
- автоматическую валидацию на основе constraints из спецификации
- HTTP-клиент для тестирования

В отличие от ручного парсинга JSON (как в `http_chi/`), ошибки несоответствия контракту ловятся на этапе компиляции.

## На что обратить внимание

| Что | Файл | Зачем |
|-----|------|-------|
| OpenAPI-спецификация | `api/weather/v1/weather.openapi.yaml` | Единый источник правды для API |
| Декомпозиция спеки | `api/weather/v1/components/`, `paths/` | Разбивка на переиспользуемые части |
| Конфигурация Ogen | `.ogen.yml` | Настройки генерации (пакет, пути) |
| Реализация Handler | `cmd/http_server/main.go` | Имплементация сгенерированного интерфейса |
| Сгенерированный код | `pkg/openapi/weather/v1/` | Не редактируется руками — перегенерируется |
| Типизированные ответы | `cmd/http_server/main.go` | Возврат конкретных типов вместо `interface{}` |

## Как запустить

```bash
task ogen:gen   # генерация кода из OpenAPI
task run        # сервер на :8080
task test:api   # API-тесты
```

## Структура проекта

```
http_chi_ogen/
├── api/weather/v1/          # OpenAPI-спецификация
│   ├── weather.openapi.yaml # корневой файл
│   ├── components/          # схемы, ошибки
│   └── paths/               # эндпоинты
├── cmd/
│   ├── http_server/         # сервер
│   └── http_client/         # клиент
├── pkg/openapi/weather/v1/  # сгенерированный код (не трогать)
├── .ogen.yml                # конфигурация Ogen
├── tests/                   # API-тесты
└── Taskfile.yaml
```
